# Level 6: テスト、評価、失敗分析

## この Level でできるようになること

コマンドパーサーと store の振る舞いをテストし、失敗を分類して改善できるようになります。

この Level の中心は、「動いた気がする」から「測って説明できる」へ進むことです。

## まず知るべき言葉

- 単体テスト: 関数や型を小さく検証するテスト。
- 統合テスト: 複数の部品を組み合わせて検証するテスト。
- 期待値: 入力に対して得られるべき結果。
- 失敗分類: 入力、I/O、状態、並行処理、運用などに分けて原因を見ること。
- 境界値: 空文字、長すぎる値、不正な形式など、壊れやすい入力。
- 回帰: 以前動いていた振る舞いが壊れること。

## なぜこれを学ぶのか

Rust は多くのメモリ安全性をコンパイル時に検査しますが、仕様の正しさまでは自動で保証しません。

たとえば、次はコンパイルできても仕様として間違っている可能性があります。

```text
SET key value extra
GET
DEL
空行
```

テストは、コードが今どう動くかだけでなく、「この仕様を今後も守る」と宣言する役割を持ちます。

## 手順 1: テストを実行する

```bash
rustc --edition=2021 --test levels/level_06_evaluation/examples/parser_tests.rs -o /tmp/zero_to_rust_parser_tests
/tmp/zero_to_rust_parser_tests
```

期待する出力には、複数の `ok` と最後の `test result: ok` が含まれます。

見るべき点は、正常系だけでなく、不正入力もテストしていることです。

## 手順 2: 失敗を分類する

KVS サーバーで起きる失敗は、少なくとも次に分けられます。

| 分類 | 例 | 対応 |
| --- | --- | --- |
| 入力エラー | `GET` のキーがない | `ERROR` を返す |
| 状態エラー | 存在しないキー | `NOT_FOUND` を返す |
| I/O エラー | 接続断、ファイル読込失敗 | `Result` で伝播する |
| 並行処理エラー | ロック競合、ロック中の I/O | ロック範囲を見直す |
| 運用エラー | ログ不足、復旧手順なし | 観測と手順を追加する |

この分類がないと、すべてが「なんか失敗した」になります。

## 手順 3: 改善前後を比較する

新しい機能を追加したら、次の順番で評価します。

```text
期待する入力を決める
期待する出力を書く
境界値を追加する
失敗時の分類を書く
テストを実行する
失敗したら原因を分類する
```

プロの改善は、感覚ではなく比較から始まります。

## よくあるつまずき

```text
Q. コンパイルが通れば安全では？
A. メモリ安全性と仕様の正しさは別です。仕様はテストやレビューで守ります。
```

```text
Q. テストで unwrap を使ってよいですか？
A. 期待する成功を短く書くために使うことはあります。ただし、失敗を検証するテストでは明示的に Err を確認します。
```

```text
Q. どこまでテストすればよいですか？
A. まずはコアロジック、パース、境界値、不正入力を押さえます。ネットワークや並行処理は後で統合テストに広げます。
```

## Rust らしさをさらに深掘りする

Rust のテストは、メモリ安全性の確認ではなく仕様の固定です。コンパイラが守ることと、テストが守ることを分けると、過信も過小評価も避けられます。
