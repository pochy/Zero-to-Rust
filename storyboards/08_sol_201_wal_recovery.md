# Sol 201: HAB 破損と WAL 復旧

対応教材: [Level 8: 運用、本番設計、復旧](../levels/level_08_production/README.md)

## 状況

二百一日目。

HAB の一部が破損した。

マークは助かった。だが、台帳データの一部が飛んだ。ジャガイモ畑も、計画の余裕も消えた。

彼は数分だけ床に座った。数分後、立ち上がった。

「泣くのはあとだ。復旧する」

メモリ上の状態は消える。操作ログがあれば戻せる。だから WAL が必要だった。

## ログ

**LOG 201.1**

マーク:

「WAL。Write-Ahead Log。操作を先に書く。状態そのものではなく、状態を作った手順を残す」

例を実行する。

```bash
rustc --edition=2021 levels/level_08_production/examples/wal_restore.rs -o /tmp/zero_to_rust_wal
/tmp/zero_to_rust_wal
```

期待する出力:

```text
restored name = Rust
restored lang = std
exists old = false
```

マーク:

「これは火星の黒匣子だ。最後の状態を信用するのではなく、そこに至る操作を再生する」

```text
SET name Rust
DEL old
SET lang std
```

起動時:

```text
WAL を先頭から読む。
各コマンドを Store に再適用する。
最後の状態を復元する。
```

## 会話

管制:

「WAL 書き込みに失敗したら、Store は更新する？」

マーク:

「それが今日の嫌な質問だ」

管制:

「答えは？」

マーク:

「整合性を優先するなら、Store を更新せず `ERROR` を返す。可用性を優先するなら、更新して `WARNING` かもしれない。だが、復旧後に消える更新は利用者を裏切る。俺の KVS では、WAL が必須なら、WAL 失敗時に更新しない」

管制:

「設定はコードに書く？」

マーク:

「書かない。火星でも環境は変わる」

```text
APP_ADDR=127.0.0.1:4000
APP_WORKERS=4
APP_DATA=/var/lib/zero-to-rust/data.wal
```

管制:

「ログには値を出す？」

マーク:

「出さない。キー名も慎重に扱う。火星で機密情報の漏えいは起きないと思うだろうが、悪い習慣は地球に帰ってから効く」

## Rust 任務

1. `wal_restore.rs` を実行する。
2. 存在するキーを削除する操作を追加し、復元後に存在しないことを確認する。
3. WAL の操作順を変えて、最終状態の違いを比較する。
4. WAL 書き込み失敗時の設計判断を書く。

演習:

- [Level 8 exercises](../levels/level_08_production/exercises.md)

## マークの独り言

「本番運用は、機能が動くことではない。壊れたあとに説明して戻せることだ」

```text
再現性:
同じ入力から同じ状態に戻せるか。

可観測性:
何が起きたかログで分かるか。

復旧性:
障害後に戻せるか。

安全性:
危険な公開や機密ログを避けているか。

限界:
std-only ではどこまでか説明できるか。
```

マーク:

「TLS、本格 HTTP、構造化ログ、複雑な CLI。標準ライブラリだけで全部やるのは賢くない場面がある。大事なのは、外部クレートを避けることではなく、採用理由を説明できることだ」

次の問いに答えられたら、Sol 401 へ進む。

```text
設定、ログ、復旧手順を本番設計に含められるか。

```
