# Sol 141: ローバー改造とスレッドプール

対応教材: [Level 7: アーキテクチャと並行処理の統合](../levels/level_07_integration/README.md)

## 状況

百四十一日目。

救助計画が変わった。マークは遠く離れた発射地点まで行く必要がある。ローバーを改造しなければならない。

やることは山ほどある。

```text
ソーラーパネルの固定
バッテリーの容量計算
酸素供給の接続
通信端末の積み込み
食料と水の配置
走行ログの記録
```

ひとつずつやるしかない。しかし、全部を単一スレッドで処理すると時間が足りない。

「よし。スレッドプールだ」

## ログ

**LOG 141.1**

マーク:

「並行処理は、作業員を増やすことに似ている。作業員を増やせば速くなる。という考えは、だいたい半分だけ正しい」

彼は例を実行した。

```bash

/tmp/zero_to_rust_thread_pool
```

期待する出力:

```text
job 0 -> 0
job 1 -> 1
job 2 -> 4
job 3 -> 9
all jobs submitted
```

ただし、ジョブの実行順は環境によって変わる。

マーク:

「並行処理で出力順に依存する設計は、砂嵐に紙の地図を持ち出すようなものだ」

## 会話

管制:

「共有 Store はどう扱う？」

マーク:

「小さく共有する。`Arc<Mutex<Store>>` だ」

管制:

「アプリ全体を `Arc<Mutex<App>>` に入れれば簡単では？」

マーク:

「簡単だ。ローバーの全ドアを一本の針金で固定するくらい簡単だ。開けたいときに全部止まる」

管制:

「ロック中にクライアントへレスポンスを書いてよいか？」

マーク:

「だめだ。ロック中は Store の更新だけにする。I/O は遅い。ロックしたまま地球との通信を待つのは、工具を握ったまま全員を待たせるようなものだ」

管制:

「`Mutex` と `RwLock` は？」

マーク:

「読み取りが圧倒的に多いなら `RwLock` を検討する。単純さと安全性を優先するなら最初は `Mutex`。火星では、賢すぎる設計も故障する」

## Rust 任務

1. `thread_pool.rs` を実行する。
2. ワーカー数を 2 から 4 に変え、出力順を観察する。
3. ジョブに `sleep` を入れ、実行順と終了順の違いを見る。
4. `Arc<Mutex<Store>>` と `Arc<RwLock<Store>>` の選択判断を書く。

- [Level 7 exercises](../levels/level_07_integration/exercises.md)

## マークの独り言

「アーキテクチャは、きれいなフォルダ構成を作る遊びではない。変更理由を分けるためにある」

```text
server:
TCP 接続と入出力。

protocol:
Command と Response。

store:
HashMap と TTL。

persist:
WAL。

error:
失敗の分類。
```

マーク:

「プロトコルを変えても Store が壊れない。Store を永続化しても TCP 層が変わらない。これが欲しい。火星で一箇所直したら三箇所爆発する設計は嫌だ」
