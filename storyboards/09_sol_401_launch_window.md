# Sol 401: 発射窓と境界チェック

対応教材: [Level 9: プロフェッショナル設計と最終課題](../levels/level_09_professional/README.md)

## 状況

四百一日目。

マークは発射地点に着いた。MAV はある。救助船も軌道上に来る。だが、条件はぎりぎりだ。

軽量化が必要。境界チェックが必要。バイト列を読み間違えれば、コマンドは壊れる。長さを確認せずに読むのは、燃料残量を見ずに点火するようなものだ。

「最後の最後で、配列の範囲外を読んで死ぬのは嫌だ」

彼は `packet_reader` を実行した。

```bash
rustc --edition=2021 levels/level_09_professional/examples/packet_reader.rs -o /tmp/zero_to_rust_packet
/tmp/zero_to_rust_packet
```

期待する出力:

```text
id = 4660
flags = 1
payload = rust
short packet rejected
```

## ログ

**LOG 401.1**

マーク:

「バイナリ処理は、文字列処理より無口だ。間違っても親切に怒ってくれない。だから先に長さを見る」

```text
[u8] を直接読む。
読む前に境界チェックする。
PacketReader を作る。
構造体へ安全に変換する。
```

マーク:

「`[0x12, 0x34]` を big endian で読むと `0x1234`。little endian なら `0x3412`。同じ二バイトでも意味が変わる。火星で向きを間違えるとだいたい遠くへ行く」

## 会話

管制:

「ここまで来た。最終判断を確認する」

マーク:

「言ってくれ」

管制:

「key と value は誰が所有する？」

マーク:

「Store が所有する。`HashMap<String, ValueEntry>` だ」

管制:

「どの関数は `&str` を受け取る？」

マーク:

「検索、削除、TTL 確認。キーを読むだけの関数は `&str`」

管制:

「共有状態は？」

マーク:

「Store を `Arc<Mutex<Store>>` か、読み取りが多ければ `Arc<RwLock<Store>>`。アプリ全体は包まない」

管制:

「WAL 書き込み失敗時は？」

マーク:

「永続化を必須にするなら Store 更新前に失敗として返す。ログだけではなく整合性の問題だ」

管制:

「std-only で不足するものは？」

マーク:

「TLS、実務品質 HTTP、構造化ログ、堅牢 CLI、非同期ランタイム。必要になったら外部クレートを採用する。採用しない勇気ではなく、採用理由を説明する力が必要だ」

## Rust 任務

1. `packet_reader.rs` を実行する。
2. `read_u32_be` を追加する。
3. 短い入力で `None` が返ることを確認する。
4. big endian と little endian の違いを説明する。
5. 最終課題の所有、失敗、共有、復旧、運用の設計メモを書く。

```text
難しい機能を使うことが目的ではない。
状況に合う責任分担を選ぶことが目的。
```

マーク:

「火星で覚えた。賢そうな設計と、生き残る設計は違う。たまに同じになる。そのときだけ採用する」
