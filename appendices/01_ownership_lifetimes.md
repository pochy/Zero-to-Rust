# 01: 所有権、借用、ライフタイム完全補講

## 目的

所有権は「メモリ管理のルール」ですが、それだけで理解すると狭すぎます。Rust では所有権が API 設計、モジュール境界、並行処理、エラー処理、パフォーマンスに直接影響します。

## まず持つべき問い

```text
この値はどこで生まれるか
誰が最後まで責任を持つか
誰が一時的に読むだけか
誰が変更してよいか
参照は何に依存しているか
複製する理由は説明できるか
```

## 所有する型を選ぶ場面

`String`、`Vec<T>`、`PathBuf`、`HashMap<K, V>` のような型は、データを自分で持ちます。次の場合は所有型が自然です。

- 関数が新しい値を作って返す
- 構造体が長く値を保持する
- 呼び出し元の寿命に依存したくない
- 別スレッドへ値を移す
- キャッシュ、保存、キュー、WAL などに入れる

```rust
struct Config {
    bind_addr: String,
    wal_path: std::path::PathBuf,
}
```

この `Config` は、呼び出し元の引数文字列に依存しません。起動後に設定を保持するなら所有型が読みやすい設計です。

## 借用を選ぶ場面

`&str`、`&[u8]`、`&Path`、`&T` は、所有者を変えずに読むための形です。

```rust
fn parse_command(line: &str) -> Result<Command, ParseError> {
    todo!()
}
```

パース関数は入力文字列を保存しません。読むだけなので `&str` が自然です。保存する必要が出た時点で、`Command` の中へ `String` として所有させます。

## 可変借用は強い権限

`&mut T` は「読むだけ」ではなく「変更してよい」という権限です。Rust は同じタイミングで複数の可変借用を許しません。

```rust
fn apply(store: &mut Store, command: Command) -> Response {
    store.execute(command)
}
```

これは Store の状態を変更する可能性を関数シグネチャに出しています。レビューでは、`&mut` がどの範囲に広がっているかを見ます。

## ライフタイムは記号ではなく依存関係

ライフタイム注釈は、参照がどの入力に依存しているかを型に書く仕組みです。

```rust
fn first<'a>(left: &'a str, _right: &str) -> &'a str {
    left
}
```

この関数の戻り値は `left` に依存します。`'a` はコンパイラへのごまかしではなく、呼び出し側へ「戻り値は left より長く生きられない」と伝える契約です。

## 構造体に参照を持たせる前に考えること

```rust
struct BadStore<'a> {
    key: &'a str,
}
```

この形は間違いではありません。ただし、`BadStore` は `key` の所有者より長く存在できません。設定、保存、キュー、キャッシュ、スレッド共有では、この制約が不自然になることが多いです。

学習初期と業務アプリの多くでは、まず所有型で構造を安定させ、必要になった場所だけ借用へ寄せます。

## `clone()` の判断

悪い `clone()`:

```text
コンパイルエラーを消すために理由なく複製する
```

良い `clone()`:

```text
所有権を分離するために複製コストを受け入れる
別スレッドへ値を渡すために小さい設定値を複製する
ログや監査用にスナップショットを残す
```

レビューで必要なのは「clone しているか」ではなく、「複製した所有者が何を担当するか」です。

## 進級チェック

```text
構造体に所有型を持たせる理由を説明できるか
関数引数に &str と String のどちらを使うか説明できるか
ライフタイムを参照の依存関係として説明できるか
clone をコストと責任の判断として説明できるか
```
