## 物語パート

気がつくと、暗かった。

目を開けたつもりだったが、そもそも目がない。手を伸ばそうとしたが、手もない。足もない。声を出そうとしても、喉がない。

ただ、ぷるん、と揺れた。

「……え、俺、これ、スライムじゃない？」

洞窟の床は冷たく、壁には青白い鉱石が淡く光っていた。前世の記憶はある。会社、会議、後輩、雨の日の横断歩道。そして、最後に考えたこと。

痛いのは嫌だ。
寒いのも嫌だ。
あと、パソコンの中身だけは処分してくれ。

そのどうしようもない願いが、どういうわけか異世界の身体に変換されたらしい。

『告。個体は新しい環境に転生しました』

「うわ、誰だ？」

『解。私は補助解析機構、大賢者です。以後、対象の状態、用語、失敗原因、標準ライブラリ相当の情報を説明します』

「標準ライブラリ相当って何？」

『告。現時点では理解不能です。まず生命維持より重要な判断があります』

「生命維持より？」

『解。この世界で最初に問うべきは、誰が何を所有するかです』

洞窟に沈黙が落ちた。

「待て。水とか食料とかじゃなくて？」

『肯定。水も食料も魔素も、所有者が曖昧なら管理不能です。Rust においても、所有者が曖昧な値は安全に扱えません』

俺はぷるぷる震えた。たぶん寒さではない。異世界に来て最初に受ける説明が、所有権だったからだ。

それでも、洞窟の床に沈んでいるだけでは何も始まらない。

俺は身体を丸めるように意識し、青白い鉱石の方へ転がった。

転がる、というより、粘液が重力に従って移動する感覚に近い。

前世なら、手をつく、足を出す、膝で踏ん張る、という順番があった。

いまは違う。

身体全体が自分であり、身体全体が道具だった。

『告。身体制御を確認。個体は単一の所有者として自己を管理しています』

「言い方がいちいちプログラムっぽいな」

『解。手足という部品単位の操作ではなく、値全体を一つの所有物として扱う状態です』

「俺の身体が値？」

『肯定。比喩です』

「比喩にしては身も蓋もない」

鉱石に近づくと、表面に水滴のような魔素が浮いていた。

俺はそれを吸い込もうとして、ふと止まった。

これを飲んだらどうなる。

この魔素は誰のものだ。

洞窟のものか。

俺が取り込んだ瞬間に俺のものになるのか。

『解。取り込むとは、所有権を得る行為です』

「やっぱりそこに戻るのか」

『肯定。外部の資源を自分の内部状態へ移すなら、以後の管理責任は個体にあります』

俺は恐る恐る魔素を吸い込んだ。

身体の内側が少し熱くなった。

痛みはない。

寒さもない。

ただ、何かが増えたという感覚だけがあった。

『告。魔素の取得に成功。内部容量に余裕があります』

「内部容量って、俺はストレージか？」

『解。保存できるものには限界があります。限界を知らずに取り込む設計は危険です』

「食べ放題じゃないのか」

『否定。無制限の所有は存在しません』

その言葉は、洞窟の壁に反響したように聞こえた。

無制限の所有は存在しない。

前世で机の上に積み上げた仕事も、未読メールも、放置したタスクも、結局は誰かが抱える責任だった。

俺は死んだ。

だが、責任という概念だけは異世界にも付いてきたらしい。

洞窟の奥へ進むと、地面に割れた石片が散らばっていた。

俺はそれを包み込もうとしたが、尖った部分が身体の表面に引っかかった。

痛くはない。

しかし、取り込んでいいものと、ただ触れるだけでいいものは違う気がした。

『提案。取得、参照、破棄を分けてください』

「取得は所有する。参照は借りる。破棄は手放す」

『解。正確です。Rust では値を所有するか、参照として借用するか、スコープ終了で破棄されるかを区別します』

「スコープって？」

『解。値が有効である範囲です。洞窟のこの区画だけで使う情報を、外へ持ち出す必要はありません』

俺は石片を取り込まず、表面だけをなぞった。

そこには細い溝が刻まれていた。

文字かもしれない。

だが、いまの俺には読めない。

「読めないものを無理に持つ必要はない、か」

『肯定。不要な所有は複雑性を増やします』

またプログラムっぽい言い方だ。

だが、その冷たさが少しだけ頼もしくもあった。

洞窟は広かった。

俺はまだ何者でもない。

名もなく、手もなく、仲間もいない。

それでも、最初の問いだけははっきりした。

何を持つのか。

何を借りるのか。

何を手放すのか。

たぶん、この問いを間違えると、どれだけ強い能力を手に入れても危ない。

『告。初期メンタルモデルの形成を確認』

「メンタルモデルって、俺の脳内地図みたいなものか」

『解。世界をどう理解するかの枠組みです』

「じゃあ俺の最初の地図は、所有権の地図ってわけだ」

『肯定』

洞窟の奥から、かすかな風が流れてきた。

風があるなら、空間が続いている。

空間が続いているなら、誰かがいるかもしれない。

俺はまだ声を持っていない。

誰かと会うなら、まず自分をどう表すかを考えなければならない。

名前。

出力。

名乗り。

大賢者が、俺の思考を先回りした。

『提案。次の段階では、個体情報を外部へ表示する方法を学習します』

「つまり、しゃべる練習？」

『解。最小の出力です』

洞窟の闇の先に向かって、俺は転がった。

『解。正確です』

「なんか地味だな。もっとこう、火を吹くとか、剣を召喚するとか」

俺は洞窟の中を転がりながら、頭の中に表を作った。


「国って。まだ俺、洞窟の床に張り付いてるだけなんだけど」

『提案。最初に小さな設計判断を身につけるべきです。小さな判断を誤る個体は、大きな国家運営でも同じ誤りを繰り返します』

「手厳しいな、大賢者」

『肯定。コンパイラも同様です』

その言葉に、俺は妙に納得した。

厳しいやつほど、序盤で止めてくれる。後で壊れるよりは、今怒られた方がいい。

『告。質問を受け付けます』

「所有権って、結局はルールなんだよな？」

『解。ルールであり、設計を強制する仕組みです』

「強制って言われると窮屈だ」

『肯定。ただし、窮屈さは事故を減らすためにあります』

『解。前世の個体は、誰が担当するか曖昧な仕事で苦しんだ経験があります』

## 大賢者による解説

『告。Rust の学習は、構文暗記ではなく設計判断から始めます』

Rust では、値には基本的に所有者が 1 つあります。所有者がスコープを抜けると、値は解放されます。別の関数に値を渡すと、所有権が移動する場合があります。

『解。所有権とは、メモリを誰が責任を持って片付けるかを型システムで表す仕組みです』

借用は、所有者を変えずに一時的に値を使う設計です。共有は、複数の処理が同じ状態に触る可能性があるため、後の Level で `Arc` や `Mutex` と一緒に学びます。

『提案。初心者は、まず次の問いを声に出してください』

```text
この値は誰が所有するのか。
この関数は所有権を受け取るのか、借りるだけなのか。
失敗したとき、この場で処理するのか、呼び出し元へ返すのか。
共有状態にする必要は本当にあるのか。
```

### 補講: 所有権を怖がらずに読むために

告。所有権は「奪い合い」ではありません。
解。Rust が見ているのは、値の面倒を最後まで見る担当者です。
あなたが `String` を作ったなら、その `String` はどこか一箇所の変数に預けられます。
その変数がスコープを抜けると、Rust は自動で片付けます。
この自動片付けを `drop` と呼びます。
大事なのは、片付ける担当が二人にならないことです。
二人が同じ荷物を同時に捨てようとすると、世界は壊れます。
Rust はその事故を、実行前に止めます。

告。借用は「一時的に見せる」約束です。
解。`&value` は、値そのものを渡すのではなく、値を見るための札を渡します。
この札を参照と呼びます。
参照を受け取った側は、基本的に値の所有者にはなりません。
だから、参照を返してもらったあとも、元の持ち主は値を使えます。
ただし、参照が生きている間は、Rust が安全な使い方か確認します。
読んでいる最中に別の場所で勝手に書き換えられると、結果が読めなくなるからです。
この「読み手と書き手の交通整理」が、借用規則です。

告。可変借用は強い力です。
解。`&mut value` は、値を書き換える権限を一時的に渡します。
書き換えは世界の状態を変える行為です。
だから、同じタイミングで複数の可変借用は作れません。
一人が倉庫の中身を書き換えている時、別の一人が同時に同じ棚を整理したら、記録が壊れます。
Rust はその状況を、コンパイル時に止めます。
これは初心者を責めるためではありません。
未来の自分を、原因不明のバグから守るためです。

解。スコープは、値が生きてよい範囲です。
`{` から `}` までの小さな部屋だと考えるとわかりやすいです。
部屋の中で作った値は、基本的に部屋を出ると片付けられます。
外の部屋から内側を見ることはできても、消えた部屋の中身を使い続けることはできません。
これが、ダングリング参照を防ぐ基本です。
ダングリング参照とは、もう存在しない値を指してしまう危険な参照です。
Rust は「死んだ荷物への地図」を作らせません。

提案。エラーを見たら、まず所有者を探してください。
「この値は今、誰のものか」
「この関数は値を受け取っただけか、所有したのか」
「参照はどこまで生きているのか」
この三つを声に出すと、コンパイラの指摘が読みやすくなります。
Rust のエラーは、敵の呪文ではありません。
大賢者が「ここで後から困ります」と先に教えてくれている報告書です。

解。ムーブは、値の所有者が変わることです。
`let b = a;` と書いたとき、型によっては `a` の中身が `b` へ移ります。
移ったあと、`a` を使おうとすると止められます。
これは `a` が空になったからというより、`a` がもうその値の担当ではないからです。
担当者でない人に仕事をさせない。
この素朴な規則が、二重解放や不正アクセスを遠ざけます。

告。コピーできる値もあります。
解。整数や真偽値のような小さく単純な値は、`Copy` として扱われることがあります。
`let y = x;` としても、`x` をそのまま使えます。
これは所有権が移動したのではなく、同じ値をもう一つ作るだけで安全だからです。
反対に、`String` のようにヒープ領域を持つ値は、勝手に複製すると片付け役が二人になります。
だからムーブになります。
どちらか迷ったら、「この値は外部の荷物を抱えているか」と考えます。

解。所有権は、Rust の全章に通じる地図です。
Level 1 の `println!` でも使います。
Level 2 のファイル読み込みでも使います。
Level 3 の `HashMap` でも使います。
Level 7 の `Arc` や `Mutex` でも、形を変えて同じ考えが出ます。
つまり、今ここで学ぶのは序盤の小技ではありません。
最後の国づくりまで続く、資源管理の基本法です。

提案。最初の練習では、完璧な設計を目指さなくてよいです。
まずは小さな値を作る。
それを別の変数に渡す。
参照で読む。
可変参照で変える。
エラーが出たら、誰が所有者かを見る。
この順番で十分です。
焦らず、値の旅を一歩ずつ追えば、Rust は読める言語になります。

## 初出用語・関数の説明

- 所有権: 値を誰が責任を持って保持し、最後に解放するかという Rust の中心ルール。
- 借用: 所有者を変えずに、一時的に値を参照して使うこと。
- スコープ: 変数が有効な範囲。スコープを抜けると、その変数が所有する値は片付けられる。
- コンパイラ: Rust のコードを実行可能な形へ変換し、所有権や型の誤りを実行前に検出する仕組み。
- 標準ライブラリ: Rust に最初から付属する基本機能群。文字列、ファイル、ネットワーク、スレッドなどを含む。

### 用語補講: 最初に迷いやすい言葉

- 所有権: 値を最後に片付ける責任のこと。
  Rust では、基本的に一つの値に一人の所有者がいます。
  所有者がスコープを抜けると、値は自動で片付けられます。
  これにより、同じメモリを二重に解放する事故を防ぎます。

- 借用: 所有者を変えずに、値を一時的に使わせること。
  `&T` は読むための借用です。
  借りた側は、値を片付ける責任を持ちません。
  「見せてもらうだけ」と考えると分かりやすいです。

- 可変借用: 値を書き換えるための借用です。
  `&mut T` と書きます。
  同じタイミングで複数作れないのが基本です。
  書き換える人を一人にすることで、状態の混乱を防ぎます。

- スコープ: 値や変数が有効な範囲です。
  多くの場合、`{` と `}` の内側です。
  範囲を出ると、その中で作られた値は片付けられます。
  エラーを読む時は、参照がどのスコープまで生きるかを見ます。

- ムーブ: 所有権が別の変数や関数へ移ることです。
  ムーブ後、元の変数はその値を使えません。
  初心者は「コピーされた」と思いがちですが、`String` などでは移動です。
  使えなくなった変数を責めず、所有者が変わったと見ます。

- `Copy`: ムーブではなく複製しても安全な型につく性質です。
  整数や真偽値など、小さく単純な型に多いです。
  `String` は通常 `Copy` ではありません。
  片付ける資源を持つ型は、勝手にコピーすると危険だからです。

- コンパイラ: Rust コードを実行可能な形へ変換し、規則違反を検査する道具です。
  この物語では、大賢者の報告として表現します。
  エラーは拒絶ではなく、危険箇所の事前報告です。
  まず一行目のエラーから読むと落ち着けます。

### 大賢者による追加解説

『告。所有権の学習で頻発する誤解を列挙します』

一つ目。

所有権は、ただのメモリ管理用語ではありません。

ファイルハンドル、ネットワーク接続、ロック、設定値、文字列、バッファ。

これらはすべて「誰が責任を持つか」を考える対象です。

二つ目。

借用は、所有権を奪わずに値を使う手段です。

読み取りだけなら共有参照を使えます。

変更したいなら可変参照が必要です。

ただし、可変参照は同時に複数持てません。

これは、同じ帳簿を二人が同時に書き換えないための規則です。

三つ目。

`clone` は逃げ道ではなく、複製コストを受け入れる設計判断です。

短い文字列なら問題にならないこともあります。

大きなデータなら性能やメモリ使用量へ影響します。

プロは、複製した理由を説明できる場所で `clone` を使います。

四つ目。

`unwrap` は、失敗しないと断言する操作です。

学習中の小さな例では便利です。

しかし、CLI、サーバ、ストレージでは、失敗時の振る舞いが仕様になります。

失敗を利用者へ返すのか。

ログへ残すのか。

終了するのか。

再試行するのか。

この判断を避けるために `unwrap` を使うと、後で設計が崩れます。

五つ目。

`Result` は、失敗を恐れる型ではありません。

失敗の可能性を関数の境界へ書き込む型です。

関数の呼び出し側は、成功と失敗の両方を読むようになります。

それが Rust の「明示的な責任」です。

### 初出用語・関数の追加説明

- 参照: 値を所有せずに使うための入口。`&value` の形で作る。
- 可変参照: 値を借りて変更する入口。`&mut value` の形で作る。
- ライフタイム: 参照が有効でいられる期間。序盤では「借りたものは持ち主より長生きできない」と考える。
- ムーブ: 所有権が別の変数や関数へ移ること。
- コピー: `i32` など一部の型で、所有権移動ではなく値が複写される振る舞い。
- ドロップ: 所有者がスコープを抜けたとき、値を片付ける仕組み。
- 二重解放: 同じ資源を二回片付けてしまう危険な誤り。Rust は所有権で防ぐ。
- データ競合: 複数の処理が同じ値を同時に不適切に読み書きする問題。
- 責務: その値や失敗を、どのコードが説明し、処理するかという担当範囲。
- 設計判断: 便利だからではなく、理由を持って選ぶこと。
