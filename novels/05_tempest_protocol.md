```rust
use std::io::{BufRead, BufReader, Write};
use std::net::TcpListener;

fn main() -> std::io::Result<()> {
    let listener = TcpListener::bind("127.0.0.1:4000")?;

    for stream in listener.incoming() {
        let mut stream = stream?;
        let mut reader = BufReader::new(stream.try_clone()?);

        let mut line = String::new();
        reader.read_line(&mut line)?;

        stream.write_all(b"OK\n")?;
    }

    Ok(())
}
```

## 大賢者による解説

『告。Level 5 の目的は、ネットワーク層とロジック層を分けることです』

`TcpListener` は TCP 接続を待ち受ける型です。`incoming()` で接続を順に受け取ります。

`TcpStream` は接続済みの相手との読み書きを表します。`BufReader` は読み込みを効率化し、行単位の読み取りに使います。

『解。ネットワークアプリでは、最低でも 3 層に分けます』

```text
TCP 入出力層
プロトコル解析層
KVS 操作層
```

この分離により、TCP を使わないテストでも `parse_command` や `Store` を検証できます。

悪い設計:

```text
接続処理の中で split し、HashMap を直接操作し、レスポンス文字列も作る。
```

良い設計:

```text
入力文字列を Command に変換する。
Command を Store に渡す。
結果を Response に変換する。
Response を wire format に変換する。
```

### 補講: TCP とプロトコルをゆっくり分ける

告。`TcpListener` は、接続を待つ門番です。
解。サーバーは、誰かが来るまで入口で待ちます。
`TcpListener::bind("127.0.0.1:4000")` のように書くと、そのアドレスとポートで待ち受けます。
`127.0.0.1` は自分のマシンを指す特別なアドレスです。
教材ではまずローカルだけで試します。
外の世界に開く前に、手元で安全に観察するためです。

解。`TcpStream` は、接続済みの相手との通り道です。
読み取りも書き込みもできます。
ただしネットワークは、ファイルよりさらに失敗します。
相手が途中で切断するかもしれません。
送ったつもりのデータが分割されて届くかもしれません。
読み込みがいつ終わるか、こちらの都合だけでは決められません。
だから、通信では「どこまでが一つの命令か」を決める必要があります。

告。プロトコルは、会話の約束です。
解。`SET key value` という一行を送るなら、空白で区切ると決めます。
`GET key` なら、キーを一つだけ読むと決めます。
`DELETE key` なら、削除対象を一つだけ指定すると決めます。
成功時は `OK`。
見つからない時は `NOT_FOUND`。
壊れた命令なら `ERROR`。
こうした返事の形まで含めて、プロトコルです。

提案。プロトコルは、曖昧さを減らすために書き出してください。
どの命令があるか。
引数はいくつか。
空白を値に含めたい時はどうするか。
改行は命令の終わりなのか。
エラー時の返答は何か。
これを決めずにコードを書き始めると、後で解釈が揺れます。
通信のバグは、たいてい「相手と自分で約束が違う」ことから生まれます。

解。`BufReader` は、読み込みを扱いやすくする包みです。
ネットワークから一文字ずつ読むと効率が悪くなります。
`BufReader` は内部にバッファを持ち、まとめて読んでから必要な分を渡してくれます。
`read_line` を使うと、改行までを一つの文字列として読めます。
一行一命令のプロトコルと相性がよいです。
ただし、相手が改行を送らないと待ち続ける可能性があります。
だから後の運用ではタイムアウトも考えます。

告。パースは、文字列を意味のある命令へ変換する作業です。
解。受け取った行は、最初はただの文字列です。
それを `Command::Set { key, value }` のような型へ変えます。
この変換に失敗することもあります。
引数が足りないかもしれません。
知らない命令かもしれません。
値が空かもしれません。
だからパースも `Result` で表すと自然です。

解。Store と通信処理は分けます。
通信処理は、接続から文字列を読みます。
パース処理は、文字列を命令にします。
Store は、命令に従って状態を更新します。
応答処理は、結果を文字列にして返します。
一つの関数に全部入れると、テストが難しくなります。
層を分けると、通信なしでも Store やパーサーを試せます。

提案。エラー応答は、利用者に優しく、攻撃者に親切すぎない形にします。
教材では学びのために、`ERROR missing key` のように理由を出してよいです。
本番では、内部情報を出しすぎない方がよいこともあります。
ただし、何が悪いか全く分からない応答は、使う人を困らせます。
「修正できる程度に説明する」がよい目安です。
この判断は、後の運用章でも繰り返し出ます。

解。`write_all` は、指定したバイト列を最後まで書こうとする関数です。
ネットワークへの書き込みは、一回で全部送れるとは限りません。
`write` は途中までしか書かない可能性があります。
`write_all` は、全部書くか、エラーになるまで続けます。
小さなサーバーでは、応答送信に `write_all` を使うと意図が明確です。
ただし、大量データでは書き込み待ちやバックプレッシャーも考える必要があります。

告。一接続一処理は、最初の足場です。
解。最初は接続を受け、命令を読み、返答して閉じる形で十分です。
この形は理解しやすく、デバッグもしやすいです。
しかし利用者が増えると、一人の処理中に他の人を待たせることになります。
そこで Level 7 のスレッドプールが必要になります。
ただし、その前に Level 6 で「本当に正しく動いているか」を試します。
動くように見える通信網ほど、境界条件で壊れやすいからです。

解。通信では、入力を信用しません。
空行が来るかもしれません。
非常に長い行が来るかもしれません。
命令の途中で切断されるかもしれません。
UTF-8 として読めないバイト列が来るかもしれません。
教材の範囲では単純化しますが、設計の目だけは持ちます。
「良い入力だけを想定しない」ことが、サーバーを書く第一歩です。

提案。Level 5 の完成条件は、派手な機能ではありません。
ローカルで接続できる。
一行の命令を読める。
命令を型に変換できる。
Store に渡せる。
結果を一行で返せる。
不正な命令に `ERROR` を返せる。
この六つがそろえば、通信網の骨格はできています。

解。次章への接続は、テストです。
人間が数回手で打って成功しても、正しいとは限りません。
同じ確認を何度も自動で行えるようにする。
失敗した時に、どの約束が破られたか分かるようにする。
それが Level 6 の役目です。
通信網は、祈りではなく検証で守ります。

告。改行コードにも小さな罠があります。
解。Unix 系では行末が `\n`、Windows では `\r\n` になることがあります。
`read_line` は行末も文字列に含めます。
命令を解釈する前に `trim_end` で行末を落とすと扱いやすくなります。
ただし `trim` を使うと、値の前後の空白まで消えることがあります。
値に空白を許す設計なら、どこまで削るかを慎重に決めます。

解。長すぎる入力への対策も考えます。
一行プロトコルは分かりやすいですが、相手が巨大な一行を送る可能性があります。
そのまま読み続けると、メモリを使いすぎるかもしれません。
教材では単純化しますが、本格運用では最大行長を決めます。
決めた上で、超えたら `ERROR line too long` のように返します。
制限は不親切ではありません。
システムを守るための境界です。

提案。応答も型にしてください。
`String` を直接返すだけだと、成功と失敗の区別が散らばります。
`enum Response` を作れば、`Ok`、`Value`、`NotFound`、`Error` を分けられます。
最後に文字列へ変換すれば、表示形式を一箇所で管理できます。
この考えは、最終課題の管理 HTTP にもつながります。
通信の外見と内部の意味を分けることが、設計を長持ちさせます。

## 初出用語・関数の説明

- `std::net::TcpListener`: TCP 接続を待ち受ける標準ライブラリの型。
- `TcpStream`: TCP 接続された相手との通信路を表す型。
- `bind`: 指定したアドレスとポートで待ち受けを開始する関数。
- `incoming()`: 入ってくる接続を順に返すメソッド。
- `std::io::BufReader`: 読み込みをバッファリングする型。
- `BufRead`: 行単位読み取りなどを提供する trait。
- `read_line`: 1 行を読み込むメソッド。
- `Write`: 書き込み機能を表す trait。
- `write_all`: 指定したバイト列をすべて書き込むメソッド。
- `try_clone`: `TcpStream` の別ハンドルを作るメソッド。
- プロトコル: 通信で使う命令と応答の決まり。
- wire format: 通信路に流す実際の文字列やバイト列の形式。

### 用語補講: 通信プロトコルの基本語

- `TcpListener`: TCP 接続を待ち受ける型です。
  サーバーの入口になります。
  `bind` でアドレスとポートを指定します。
  接続が来ると `TcpStream` を受け取れます。

- `TcpStream`: 接続済みの相手と読み書きするための型です。
  クライアントとの通り道です。
  読み込みも書き込みも失敗する可能性があります。
  ネットワークは常に途中切断を想定します。

- `bind`: 待ち受けるアドレスを確保する操作です。
  すでに使われているポートでは失敗します。
  権限がないポートでも失敗します。
  だから戻り値は `Result` です。

- ポート: 同じマシン内で通信の入口を区別する番号です。
  `127.0.0.1:4000` の `4000` がポートです。
  教材ではローカルの番号を使います。
  本番では衝突や公開範囲に注意します。

- `BufReader`: 読み込みを効率よく扱うための包みです。
  内部にバッファを持ちます。
  `read_line` と組み合わせると、一行プロトコルを扱いやすくなります。
  ただし相手が改行を送らない場合は待ち続ける可能性があります。

- `read_line`: 改行までを読み込むメソッドです。
  読んだ内容は `String` に追加されます。
  行末の改行も含まれるため、必要なら `trim_end` します。
  何バイト読めたかも結果として返します。

- `write_all`: 指定したデータを最後まで書こうとするメソッドです。
  ネットワークでは、一度の `write` で全部送れないことがあります。
  `write_all` は、全部書くかエラーになるまで続けます。
  短い応答を確実に送る時に分かりやすいです。

- プロトコル: 通信の約束です。
  命令の形、引数の数、応答の形を決めます。
  約束が曖昧だと、送る側と受ける側で解釈がずれます。
  先に文章で書いてから実装すると安全です。

- パース: 文字列を意味のある型へ変換することです。
  `SET a b` を `Command::Set` にするような処理です。
  失敗する可能性があるため `Result` と相性がよいです。
  パースを分けると、通信なしでテストできます。

- `trim_end`: 文字列末尾の空白や改行を取り除くメソッドです。
  `read_line` 後の改行処理でよく使います。
  `trim` は先頭の空白も消すため、値の意味が変わる場合があります。
  どこを削るかはプロトコルの仕様です。

- `enum Response`: 応答の種類を型で表す設計例です。
  成功、値あり、見つからない、エラーを分けられます。
  最後に文字列へ変換すれば、外見を一箇所で管理できます。
  型にすると、応答漏れを減らせます。

- `ERROR`: 不正入力や処理失敗を伝える応答です。
  何でも `ERROR` にすると原因が分かりにくくなります。
  教材では短い理由を添えると学びやすいです。
  本番では情報を出しすぎない配慮も必要です。

### 大賢者による追加解説

`TcpListener` は、TCP 接続を待ち受ける型です。

`TcpListener::bind("127.0.0.1:4000")` のように、アドレスとポートへ束縛します。

`127.0.0.1` は自分自身を指すローカルアドレスです。

`4000` はポート番号です。

ポートは、同じ機械の中でどのサービスへ接続するかを分ける番号です。

`listener.incoming()` は、接続を順に受け取るイテレータです。

各要素は `Result<TcpStream, std::io::Error>` です。

接続受け入れにも失敗があるためです。

`TcpStream` は、接続済みの読み書き可能な通信路です。

`std::io::BufReader` は、読み込みをバッファリングする型です。

一 byte ずつ読むより効率よく、`read_line` のような便利な読み方もできます。

`read_line` は、改行まで読みます。

戻り値は読み込んだ byte 数です。

`0` が返った場合、相手が接続を閉じたことを意味します。

`write_all` は、指定した byte 列をすべて書き込むまで試みます。

途中までしか書けない可能性があるため、単なる `write` より扱いやすい場面があります。

`flush` は、バッファに残っている出力を実際に送り出します。

### プロトコルを先に決める

通信処理では、コードより先に wire format を決めます。

wire format は、通信路を流れる実際の文字列や byte 列の形です。

最小 KVS なら、次のような形にできます。

```text
SET key value
GET key
DEL key
QUIT
```

応答は次のようにできます。

```text
OK
VALUE value
NOT_FOUND
ERR message
BYE
```

ここで大切なのは、曖昧さを減らすことです。

`SET key value` の `value` に空白を許すのか。

キーに空白を許すのか。

大文字小文字を区別するのか。

空行はエラーか。

引数が多すぎる場合はどうするのか。

これらを決めないまま実装すると、あとで互換性が壊れます。

学習用なら制約を小さくして構いません。

キーは空白なし。

値も空白なし。

命令は大文字。

一行一命令。

最初はそれでよいです。

ただし、制約は書いておきます。

### パーサを分ける

通信処理の中で、その場で文字列を分解すると、すぐ読みにくくなります。

そこで、文字列から `Command` へ変換する関数を分けます。

```rust
enum Command {
    Set { key: String, value: String },
    Get { key: String },
    Del { key: String },
    Quit,
}
```

`parse_command(line: &str) -> Result<Command, String>` のようにします。

成功すれば `Command`。

失敗すればエラーメッセージ。

ここでは学習用に `String` エラーでも構いません。

ただし、後で分類したくなるなら、`enum ParseError` を作るとよいです。

パーサを分けると、テストしやすくなります。

TCP サーバを起動しなくても、文字列から命令への変換を確認できます。

これは Level 6 のテストへつながります。

### 通信失敗の分類

通信では、失敗の種類が増えます。

接続を受け入れられない。

読み込み中に切断される。

書き込みに失敗する。

命令の形式が間違っている。

Store 操作で失敗する。

これらをすべて `ERR` にしても、外からは区別できません。

最初は単純でよいです。

ただし、内部ログでは分類してください。

後で運用するとき、どの失敗が多いか分からないと改善できません。

### 初出用語・関数の追加説明

- TCP: 順序と再送を扱う信頼性のあるバイト列通信プロトコル。

- ポート: 同じ機械上のサービスを区別する番号。

- `write_all`: 指定した byte 列を最後まで書き込むメソッド。

- 接続: 通信相手との読み書き可能な関係。
- 切断: 相手が接続を閉じること。
