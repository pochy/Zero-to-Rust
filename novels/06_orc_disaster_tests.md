## 会話・独白パート

智慧之王が、淡々とコードを示す。

```rust
#[derive(Debug, PartialEq)]
enum Command {
    Set { key: String, value: String },
    Get { key: String },
    Delete { key: String },
    Quit,
}

fn parse_command(input: &str) -> Result<Command, String> {
    let parts: Vec<&str> = input.trim().splitn(3, ' ').collect();

    match parts.as_slice() {
        ["SET", key, value] => Ok(Command::Set {
            key: key.to_string(),
            value: value.to_string(),
        }),
        ["GET", key] => Ok(Command::Get {
            key: key.to_string(),
        }),
        ["DEL", key] => Ok(Command::Delete {
            key: key.to_string(),
        }),
        ["QUIT"] => Ok(Command::Quit),
        _ => Err(format!("invalid command: {}", input.trim())),
    }
}
```

『解。テスト関数として実行対象にする属性です』

「属性？」

『解。コンパイラやツールに追加情報を渡すための記法です』

『肯定。実行時の能力ではなく、検証能力が増えます』

「`assert_eq!` は？」

『解。左右の値が等しいことを確認するマクロです。等しくなければテストが失敗します』

## 智慧之王による解説

『告。Level 6 の目的は、「動いた」を検証可能な仕様に変えることです』

テストは、コードが期待通りに動くことを確認するだけではありません。仕様の境界を明確にする作業です。

失敗は分類します。

```text
入力エラー: 不正なコマンド
I/O エラー: 接続断、ファイル読み込み失敗
状態エラー: 存在しないキー
並行処理エラー: ロック競合
設計エラー: 巨大な main.rs
運用エラー: ログ不足
```

『解。分類できない失敗は、改善できません』

`#[test]` を付けた関数は、`cargo test` で実行されるテストになります。`assert_eq!` は、左右の値が等しいことを確認します。

```rust
#[test]
fn parse_set_command() {
    let command = parse_command("SET name rust").unwrap();

    assert_eq!(
        command,
        Command::Set {
            key: "name".to_string(),
            value: "rust".to_string()
        }
    );
}
```

ここでの `unwrap()` は、テストの前提として成功を期待しているため許容できます。失敗した場合はテストが落ち、問題が明確になります。

### 補講: テストを怖がらず、仕様の味方にする

告。ここからは智慧之王が、実装を設計として検査します。
解。テストは、失敗を責める儀式ではありません。
何を守りたいかを、コードで書いた契約です。
人間は忘れます。
仕様も成長します。
昨日動いたものが、今日の変更で壊れることもあります。
テストは、その変化を早く知らせる見張りです。

解。`#[test]` は、この関数をテストとして実行する印です。
`cargo test` は、その印がついた関数を探して実行します。
関数の中で期待と違うことが起きると、テストは失敗します。
失敗は悪い知らせではあります。
しかし、利用者の前で壊れる前に見つかったなら、よい知らせでもあります。
オーク災厄を町に入れる前に、城門で止めるようなものです。

告。`assert_eq!` は、期待と実際を比べます。
解。`assert_eq!(actual, expected)` は、二つの値が等しいことを確認します。
違っていれば、テストは失敗し、どちらが何だったかを表示します。
`assert!` は、条件が真であることを確認します。
`assert_ne!` は、二つの値が違うことを確認します。
どれを使うかは、「何を読者に伝えたいか」で選びます。
値の差を見たいなら `assert_eq!` が親切です。

解。単体テストは、小さな部品を試します。
パーサーだけ。
Store だけ。
TTL の判定だけ。
このように狭い範囲を試すと、失敗原因を見つけやすくなります。
通信やファイルを使わず、純粋な関数として試せるなら、単体テストに向いています。
小さな部品ほど、何度も速く試せます。
速いテストは、開発中に繰り返し実行できます。

解。統合テストは、部品を組み合わせて試します。
サーバーを起動して接続する。
命令を送り、応答を読む。
WAL を書き、再起動して復旧を確認する。
このようなテストは、現実の使い方に近いです。
ただし準備が重く、失敗原因の切り分けも難しくなります。
単体テストと統合テストは、どちらか一方ではありません。
小さな契約と大きな流れを、両方守ります。

提案。テスト名は、物語の見出しのように書いてください。
`test1` では、何を守っているかわかりません。
`get_returns_none_for_missing_key` なら、期待が読めます。
`set_overwrites_existing_value` なら、上書き仕様が読めます。
`invalid_command_returns_error` なら、不正入力の扱いが読めます。
テスト名を読むだけで仕様一覧になるのが理想です。
未来の自分が助かります。

告。失敗分類は、設計の地図です。
解。失敗には種類があります。
正常系の期待違い。
入力エラー。
境界条件。
I/O 失敗。
並行処理の競合。
復旧手順の漏れ。
これらを同じ「バグ」でまとめると、対策がぼやけます。
分類すると、どの層を直すべきか見えます。

解。境界条件は、端の世界です。
空文字列。
存在しないキー。
非常に長い入力。
同じキーの上書き。
削除後の再取得。
ゼロ秒 TTL。
こうした端の条件は、普通の成功例よりバグを見つけやすいです。
初心者ほど、気持ちよく成功する例だけで満足しがちです。
智慧之王は、端を見ます。

提案。テストデータは、意味を持たせすぎないでください。
`alice` や `sword` のような名前は読みやすいです。
しかし物語上の意味に引っ張られて、仕様が見えにくくなることもあります。
`key1`、`value1` の方がよい場合もあります。
テストで大切なのは、何を検証しているかが一目で分かることです。
教材では、読みやすさと仕様の明確さを優先します。

解。`unwrap()` は、テストでは許される場面があります。
準備処理が失敗したら、そのテストは続けられません。
その場合、`unwrap()` で落としても、失敗箇所が明確なら実用的です。
ただし、検証したい失敗を `unwrap()` で潰してはいけません。
エラーを返すこと自体を確認したいなら、`is_err()` や `match` で確認します。
何をテストしているのかを、常に中心に置きます。

告。テストは、実装より先に書いても、後に書いても価値があります。
解。先に書くと、仕様がはっきりします。
後に書くと、今の振る舞いを固定できます。
バグ修正の時は、まず失敗するテストを書くと再発防止になります。
この教材では、手を動かしながら必要なテストを増やします。
完璧なテスト戦略を最初から作る必要はありません。
壊れた場所から、守る範囲を広げていけばよいです。

解。テストしやすい設計は、使いやすい設計でもあります。
通信処理と Store が分かれていれば、Store だけを試せます。
パース処理が関数になっていれば、文字列だけで試せます。
時刻を直接読む処理を分ければ、TTL も試しやすくなります。
テストが書きにくい時は、設計の責任が混ざっている合図かもしれません。
智慧之王は、テスト失敗だけでなく、テストしにくさも観測します。

提案。`cargo test` の結果は、数だけ見ないでください。
何件通ったか。
何件失敗したか。
どのテストが失敗したか。
失敗メッセージは期待と実際を示しているか。
この四つを確認します。
失敗メッセージが読みにくいなら、テストを直す価値があります。
よいテストは、壊れた時に修理の入口を示します。

告。次章では、同時に来る接続を扱います。
解。テストで失敗の種類を見た後、国は利用者の増加に向き合います。
一人ずつ処理すれば簡単です。
しかし接続が増えると、待ち時間が問題になります。
そこでスレッド、共有状態、ロックが登場します。
並行処理は強力ですが、テストなしで入ると危険です。
Level 6 の検証力を持ったまま、Level 7 の組織運営へ進みます。

告。テストは、仕様変更の会議録にもなります。
解。たとえば、空の値を許すかどうかを決めたとします。
許すなら、そのテストを書きます。
許さないなら、`ERROR` になるテストを書きます。
後で誰かが実装を変えた時、テストが「この国ではこう決めた」と教えます。
口頭の約束より、実行できる約束の方が強いです。

解。テストの失敗は、三段階で読みます。
まず、どのテスト名が失敗したかを見ます。
次に、期待値と実際値を見ます。
最後に、最近変えた箇所と照らし合わせます。
慌てて実装を触る前に、失敗が何を意味しているかを言葉にします。
「この入力で、この応答を期待したが、別の応答になった」
この一文が作れれば、修正はかなり近づきます。

提案。壊れたテストを消して進まないでください。
テストが古い仕様を守っている場合は、先に仕様変更を明文化します。
その上でテストを直します。
実装に都合が悪いから消すのは、城壁を外すのと同じです。
守るものを変えるなら、理由を残します。
これが、智慧之王の設計レビューです。

解。テストは数よりも網羅の形が大切です。
似た成功例を十個並べても、境界条件が抜けていれば不安は残ります。
正常系、不正入力、存在しない対象、上書き、削除、復旧。
こうした種類を並べると、守っている範囲が見えます。
不足している種類が見えたら、そこに一つ足します。
やみくもに増やさず、分類して増やします。

## 初出用語・関数の説明

- `#[test]`: テスト関数であることを示す属性。
- `cargo test`: Rust のテストをコンパイルして実行する Cargo コマンド。
- `assert_eq!`: 2 つの値が等しいことを確認するマクロ。
- `PartialEq`: 値同士の等価比較を可能にする trait。
- `Debug`: テスト失敗時などに値を表示しやすくする trait。
- `splitn`: 文字列を指定回数まで分割するメソッド。
- `trim`: 文字列の前後の空白や改行を取り除くメソッド。
- `match`: 値の形に応じて処理を分岐する構文。
- 単体テスト: 小さな関数やモジュール単位のテスト。
- 統合テスト: 複数の部品を組み合わせた動作を確認するテスト。
- 失敗分類: エラーを原因や責務ごとに分け、対応方針を決めること。

### 用語補講: テストで使う基本語

- `#[test]`: 関数をテストとして扱う属性です。
  `cargo test` がこの印を探して実行します。
  テスト関数は普通の Rust 関数として書けます。
  名前は仕様が読めるように付けます。

- 属性: `#[...]` の形で、コンパイラやツールへ情報を伝える仕組みです。
  `#[test]` はその一つです。
  `#[derive(Debug)]` のような属性もあります。
  まずは「関数や型に付ける目印」と考えると分かりやすいです。

- `cargo test`: Rust のテストを実行するコマンドです。
  単体テストと統合テストをまとめて実行できます。
  失敗したテスト名と失敗内容を表示します。
  変更後に繰り返し実行する習慣を作ります。

- `assert!`: 条件が真であることを確認するマクロです。
  条件が偽ならテストは失敗します。
  単純な真偽の確認に向いています。
  期待値と実際値を見たい時は `assert_eq!` が親切です。

- `assert_eq!`: 二つの値が等しいことを確認するマクロです。
  違っていれば、期待と実際の差を表示できます。
  Store の取得結果などを確認する時に便利です。
  テスト失敗時の読みやすさを考えて選びます。

- 単体テスト: 小さな部品を個別に試すテストです。
  パーサー、Store、TTL 判定などに向いています。
  失敗原因を絞り込みやすいです。
  速く実行できるので、開発中に何度も回せます。

- 統合テスト: 複数の部品を組み合わせて試すテストです。
  TCP サーバーに接続して応答を見るような確認です。
  現実の使い方に近い一方で、準備が重くなります。
  単体テストと組み合わせて使います。

- 境界条件: 入力や状態の端にあるケースです。
  空文字、存在しないキー、長すぎる入力、ゼロ秒 TTL などです。
  成功例だけでは見つからないバグを出しやすいです。
  テストでは意識して追加します。

- 回帰: 以前直したバグや動いていた機能が、変更でまた壊れることです。
  回帰テストは、それを防ぐためのテストです。
  バグを直したら、そのバグを再現するテストを残すと強いです。
  未来の変更から現在の仕様を守れます。

- 期待値: テストで「こうなるはず」と決めた値です。
  実際値と比較します。
  期待値が曖昧だと、テストの意味も曖昧になります。
  先に言葉で仕様を書くと決めやすくなります。

- フィクスチャ: テストの前提として用意するデータや状態です。
  一時ファイル、初期 Store、サンプル命令などが該当します。
  準備が複雑すぎると、テスト本体が読みにくくなります。
  何を検証するための準備かを意識します。

### 智慧之王による追加解説

Rust のテストは、標準機能で書けます。

`#[test]` を付けた関数は、テストとして実行されます。

`cargo test` を使う構成ならまとめて実行できます。

この教材では `rustc --test` で個別ファイルを実行する例もあります。

`assert_eq!(left, right)` は、二つの値が等しいことを確認します。

`assert!(condition)` は、条件が true であることを確認します。

`#[cfg(test)]` は、テスト時だけ有効になるコードを囲むために使います。

テスト用の helper 関数やモジュールを、本番ビルドへ入れたくないときに便利です。

単体テストは、部品の振る舞いを確認します。

統合テストは、複数の部品が組み合わさった振る舞いを確認します。

失敗分類は、失敗を「何が悪いか」で分ける作業です。

解析失敗。

入力不足。

状態不整合。

I/O 失敗。

接続切断。

これらを同じ「失敗」とだけ呼ぶと、修正も運用も難しくなります。

### テストケースを物語にする

テストケースは、小さな事件です。

事件には前提があります。

操作があります。

期待する結果があります。

例えば、存在しないキーを読む事件。

```text
前提: Store は空である。
操作: GET food を実行する。
期待: NOT_FOUND が返る。
```

削除後に読む事件。

```text
前提: food=rice が保存されている。
操作: DEL food の後に GET food を実行する。
期待: 最初は OK、次は NOT_FOUND。
```

構文エラーの事件。

```text
前提: 入力行が "SET food" である。
操作: parse_command を実行する。
期待: 引数不足のエラーになる。
```

こうして書くと、テストは物語の検証になります。

「こういう状況なら、こう振る舞う」

それをコードにしたものがテストです。

### 小さなテスト例

```rust
#[test]
fn parse_get_command() {
    let command = parse_command("GET food").unwrap();
    assert_eq!(command, Command::Get { key: "food".to_string() });
}
```

この例には前提があります。

`Command` が `PartialEq` と `Debug` を実装している必要があります。

比較するために `PartialEq`。

失敗時に表示するために `Debug`。

学習用なら、次のように derive できます。

```rust
#[derive(Debug, PartialEq)]
enum Command {
    Get { key: String },
}
```

`derive` は、よく使う実装を自動生成する仕組みです。

ただし、自動生成でよいかどうかは型の意味によります。

`Command` の比較なら自然です。

パスワードや機密情報を含む型の `Debug` は慎重に考えます。

### 失敗テストも書く

成功ケースだけのテストは、国の祭りの日だけ見て政治を語るようなものです。

悪天候の日も必要です。

不正な命令。

足りない引数。

多すぎる引数。

空文字。

存在しないキー。

削除済みキー。

読み込み失敗。

これらを入れると、仕様が強くなります。

```rust
#[test]
fn reject_incomplete_set() {
    let result = parse_command("SET food");
    assert!(result.is_err());
}
```

`is_err` は、`Result` が `Err` かどうかを調べるメソッドです。

同様に `is_ok` は `Ok` かどうかを調べます。

ただし、エラー内容まで確認したい場合は、`match` や `unwrap_err` を使います。

学習中は `unwrap_err` で観察しても構いません。

本番コードでは、利用者へ返すエラーの形を丁寧に設計します。
