## 智慧之王による解説

『告。Level 8 の目的は、本番運用を意識して設定、ログ、復旧を設計することです』

設定はコードに固定せず、環境変数や設定ファイルから読み取ります。

```rust
use std::env;
use std::net::SocketAddr;

#[derive(Debug)]
struct Config {
    addr: SocketAddr,
    worker_count: usize,
    data_path: String,
}
```

`WAL` は、操作をログとして残し、再起動時に読み直して状態を復元する仕組みです。

```text
WAL を先頭から読む
各コマンドを Store に再適用する
最後の状態を復元する
```

『解。復旧手順は、障害が起きてから考えるものではありません。設計時に決めます』

標準ライブラリだけでできることと難しいことも区別します。TCP サーバー、ファイルログ、環境変数、簡易 HTTP は可能です。一方で、完全な HTTP、TLS、構造化ログ基盤、高品質 JSON パーサーは外部ライブラリや周辺コンポーネントを検討します。

### 補講: 運用は、壊れた後も続く設計である

告。WAL は write-ahead log の略です。
解。状態を変更する前に、その変更内容をログへ書く考え方です。
先に記録してから、メモリ上の Store を更新します。
もし途中でプロセスが落ちても、ログを読み直せば変更を再現できます。
これは完全な魔法ではありません。
どのタイミングで書き込みを確定したとみなすか、慎重に決める必要があります。
それでも、永続化の第一歩としてとても重要です。

解。普通のログと WAL は目的が違います。
普通のログは、人間が状況を読むための記録です。
「接続を受けた」「エラーが起きた」「復旧を開始した」などを書きます。
WAL は、機械が状態を復元するための記録です。
`SET key value` や `DELETE key` のように、再実行できる形で残します。
この二つを混ぜると、復旧処理が読みにくくなります。
人間向け記録と機械向け記録を分けます。

告。復旧は、起動時の仕事です。
解。サーバーが立ち上がった時、WAL を先頭から読みます。
記録された命令を順番に Store へ適用します。
すると、落ちる前に近い状態を再構築できます。
ただし壊れた行があるかもしれません。
途中までしか書けていない行があるかもしれません。
教材では単純な行単位 WAL から始めます。
壊れた末尾をどう扱うかも、運用判断として記録します。

提案。WAL の書き込みタイミングを言葉で決めてください。
命令を受け取る。
検証する。
WAL に書く。
必要なら flush する。
Store を更新する。
応答を返す。
この順序を曖昧にしないことが大切です。
順序が変わると、クラッシュ時に「返事はしたのに残っていない」などの問題が起きます。

解。`flush` は、バッファにあるデータを外へ押し出す操作です。
書き込み処理は、効率のために一時的にメモリへためることがあります。
`flush` すると、少なくともライブラリのバッファから先へ送ろうとします。
ただし、OS やディスクの完全な永続化まで保証するには、さらに別の考えが必要です。
標準ライブラリだけでも学べますが、本番データベースの耐久性はもっと深い分野です。
ここでは、耐久性には段階があると理解します。

告。環境変数は、実行時の設定を外から渡す仕組みです。
解。`std::env::var("PORT")` のように読むと、環境に設定された値を取得できます。
ポート番号、ログレベル、データディレクトリなどをコードに直書きしないために使います。
ただし環境変数は文字列です。
数値として使うならパースが必要です。
設定値がない場合や壊れている場合も、`Result` や `Option` で扱います。

解。設定には既定値が必要です。
毎回すべての設定を指定しないと動かないプログラムは、使いにくくなります。
たとえばポートは `4000`、データディレクトリは `./data` など、学習用の既定値を置けます。
ただし本番では、意図しない既定値で動く危険もあります。
重要な設定は起動時に表示する。
危険な設定は明示を要求する。
このような判断も運用設計です。

提案。ログには、利用者の秘密を安易に書かないでください。
キーや値に機密情報が含まれる可能性があります。
学習中は見やすさのために表示してもよいですが、運用では注意します。
「何が起きたか」は知りたい。
「秘密そのもの」は出したくない。
この線引きを早めに意識すると、ログ設計が丁寧になります。

解。復旧手順は、コードだけでなく文章にもします。
サーバーを止める方法。
WAL の場所。
再起動時に何が起きるか。
壊れた WAL を見つけた時の対応。
バックアップを戻す手順。
これらは、README や runbook に書く価値があります。
夜中に障害が起きた時、未来の自分は文章に救われます。

告。バックアップは、WAL とは別の守りです。
解。WAL は最近の変更を再生するための記録です。
バックアップは、ある時点の状態を別の場所に残すことです。
同じディスクにだけ置いていると、ディスク障害には弱いです。
教材では深く実装しませんが、運用の視点として触れます。
データを持つシステムは、消えた時の責任も持ちます。

解。std-only には限界があります。
標準ライブラリだけでも、学習用の WAL、ログ、TCP、スレッドは作れます。
しかし本番では、成熟したクレートやデータベースを使う判断も重要です。
今回あえて std-only にするのは、仕組みの骨格を理解するためです。
車輪を再発明して本番投入するためではありません。
仕組みを知ると、既存の道具を選ぶ目も育ちます。

提案。Level 9 では、限界を見た上で設計判断を学びます。
バイナリ処理はいつ必要か。
`unsafe` はいつ避け、いつ検討するのか。
DNS や SHA や圧縮のような専門領域を、どこまで自作するのか。
WAL を経験した今なら、「作れる」と「作るべき」は違うと分かります。
運用章の学びは、高度設計の入口です。

告。障害対応では、時系列が重要です。
解。いつ起動したか。
いつ接続が増えたか。
いつエラーが出たか。
いつ復旧を始めたか。
ログに時刻があると、この順番を追えます。
標準ライブラリだけでは高度なログ基盤は作りませんが、時系列を残す意識は持てます。
問題の原因は、単独の一行ではなく流れの中にあります。

解。WAL の肥大化も運用課題です。
変更をすべて追記すると、ファイルは大きくなります。
起動時の再生にも時間がかかります。
ある時点の Store 全体をスナップショットとして保存し、それ以前の WAL を整理する設計があります。
教材では実装必須にしません。
しかし「追記ログはいつか整理が必要になる」と知っておくと、次の設計判断ができます。

提案。復旧テストは、実際にプロセスを落とす前に小さく作れます。
Store に命令を適用する。
WAL に同じ命令を書く。
新しい Store を作る。
WAL を読み直す。
期待した値が戻るか確認する。
この流れなら、復旧の中心部分を自動テストできます。
本物のクラッシュ試験は、その後の発展として扱えます。

## 初出用語・関数の説明

- `std::env::var`: 環境変数を読み取る関数。
- `SocketAddr`: IP アドレスとポートをまとめた型。
- `parse`: 文字列を指定した型へ変換するメソッド。
- `unwrap_or_else`: 値がない場合や失敗した場合に、代替値を遅延生成するメソッド。
- `map_err`: エラー値を別の型へ変換するメソッド。
- WAL: Write-Ahead Log。状態変更をログに残し、復旧に使う仕組み。
- 環境変数: 実行環境からプログラムへ渡す設定値。
- 可観測性: システム内部の状態をログやメトリクスから把握できる性質。
- 復旧性: 障害後に正常状態へ戻せる性質。
- bind address: サーバーが待ち受ける IP アドレスとポート。
- リバースプロキシ: 外部からの通信を受け、内部サーバーへ中継する仕組み。
- TLS: 通信を暗号化し、相手を検証するための仕組み。

### 用語補講: 運用と復旧の言葉

- WAL: write-ahead log の略です。
  状態を変える前に、変更内容を先に記録する考え方です。
  クラッシュ後にログを再生して状態を戻せます。
  ただし、どこまで耐久性を保証するかは設計次第です。

- ログ: 人間が出来事を読むための記録です。
  接続、エラー、起動、復旧などを書きます。
  WAL とは目的が違います。
  人間向けログに機械復旧の責任を持たせないようにします。

- 復旧: 障害後に使える状態へ戻すことです。
  WAL の再生、バックアップの復元、設定確認などが含まれます。
  コードだけでなく手順書も必要です。
  復旧できることは、テストで確認します。

- `flush`: バッファにたまったデータを外へ押し出す操作です。
  書いたつもりのデータが、まだ内部に残っている場合があります。
  WAL では書き込みタイミングの理解が重要です。
  完全な耐久性には OS やディスクの事情も関係します。

- 環境変数: 実行時に外から渡す設定値です。
  ポート番号やデータディレクトリを切り替える時に使えます。
  `std::env::var` で読みます。
  値は文字列なので、必要なら数値へ変換します。

- `std::env::var`: 指定した環境変数を読む関数です。
  設定がない場合はエラーになります。
  既定値を使うか、起動エラーにするかは設計判断です。
  設定読み込みも `Result` と相性がよいです。

- 既定値: 設定が指定されない時に使う値です。
  学習用には便利です。
  ただし本番では、意図しない既定値で動く危険もあります。
  起動時に設定を表示すると確認しやすくなります。

- runbook: 障害対応や運用手順を書いた文書です。
  どこを見るか、どう再起動するか、どう復旧するかを書きます。
  夜中の作業では、記憶より手順書が頼りになります。
  最終課題でも短い手順を書く価値があります。

- バックアップ: データを別の場所や時点に保存することです。
  WAL だけでは守れない障害があります。
  ディスクごと壊れた場合、別場所のバックアップが必要です。
  教材では概念として押さえます。

- スナップショット: ある時点の状態全体を保存したものです。
  WAL が大きくなりすぎた時の整理に使えます。
  スナップショット以降の WAL だけ再生すれば復旧が速くなります。
  実装は発展ですが、考え方は重要です。

- std-only: 標準ライブラリだけで作る方針です。
  仕組みを理解するには良い制約です。
  便利な外部クレートを使わない分、自分で判断する範囲が増えます。
  本番では、標準だけにこだわらず適切な道具を選びます。

### WAL の最小形式

学習用の WAL は、まず一行一操作にできます。

```text
SET key value
DEL key
SETEX key ttl_seconds value
```

復旧時には、この行を順に解析します。

`SET` なら Store へ保存します。

`DEL` なら Store から削除します。

`SETEX` なら期限付きで保存します。

ここでもプロトコル設計と同じ問題が出ます。

値に空白を許すのか。

キーに空白を許すのか。

時刻は相対秒か絶対時刻か。

壊れた行をどう扱うのか。

WAL は内部形式だから雑でよい、とはなりません。

内部形式ほど、将来の自分が読むことになります。

### 復旧手順を物語にする

```text
1. 新しい空の Store を作る。
2. WAL ファイルを開く。
```

これらが必要です。

### ログと標準出力

CLI やサーバでは、通常応答と診断情報を分けます。

クライアントへ返すプロトコル応答は通信路へ書きます。

管理者向けの診断は標準エラーやログファイルへ書きます。

`println!` で何でも出すと、プロトコル応答へ余計な文字が混ざる危険があります。

学習用の TCP サーバでも、この区別は守るべきです。

`eprintln!` を使えば、標準エラーへ出せます。

本格的なログレベルや構造化ログは外部クレートが便利です。

ただし、この教材では std-only の範囲で、まず出力先と目的を分けます。

### 初出用語・関数の追加説明

- WAL: Write-Ahead Log。状態変更前に操作を記録し、復旧に使うログ。
- 耐久性: プロセス停止や再起動後もデータが残る性質。
- 復旧: 保存された記録から状態を再構築すること。
- `std::env::args`: CLI 引数を取得する関数。
- `std::env::var`: 環境変数を取得する関数。
- 環境変数: 実行環境からプログラムへ渡す設定値。
- `OpenOptions`: ファイルを読み書き追記など細かい条件で開くための型。
- 追記: 既存内容の末尾へ新しい内容を書き足すこと。
- `flush`: バッファ内容を出力先へ送る操作。
- sync: OS やストレージへ書き込みをより強く反映させる操作。
- ログレベル: 情報、警告、エラーなどログの重要度。
- 運用手順: 起動、停止、監視、復旧を人間が実行できる形で書いた手順。
- ハードコード: 設定値をコードへ直接固定してしまうこと。
