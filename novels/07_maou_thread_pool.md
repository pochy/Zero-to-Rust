## 智慧之王による解説

『告。Level 7 の目的は、中規模コードに耐えるレイヤー分割と並行処理です』

`Arc<T>` は、複数スレッドから同じ値を共有するための参照カウント付きスマートポインタです。`Mutex<T>` は、同時に 1 つの処理だけが中身にアクセスできるように保護します。

`Arc<Mutex<Store>>` は、複数スレッドで `Store` を共有しつつ、更新時にロックする典型的な形です。

『解。ただし、これは便利な万能薬ではありません』

危険な設計:

```rust
type SharedEverything = Arc<Mutex<App>>;
```

より良い設計:

```rust
type SharedStore = Arc<Mutex<Store>>;
```

共有対象を小さくし、ロック範囲を短くします。ロック中にネットワーク I/O をすると、他の処理が待たされます。

`mpsc` は、複数の送信者から 1 つの受信者へメッセージを送るチャンネルです。スレッドプールでは、ジョブをキューへ送り、ワーカーが受け取って実行します。

### 補講: 並行処理を組織運営として理解する

告。スレッドは、同じプログラム内で別々に進む仕事の流れです。
解。一人の worker が一つの接続を処理している間、別の worker が別の接続を処理できます。
これにより、待ち時間の長い処理が全体を止めにくくなります。
ただし、同時に進むということは、同じデータへ同時に触る危険も増えます。
並行処理は、速さだけの技術ではありません。
責任分担と衝突防止の技術です。

解。`Arc` は、複数スレッドで所有権を共有するための道具です。
`Rc` という単一スレッド用の共有所有もありますが、スレッド間では使えません。
`Arc` は atomic reference counting の略です。
参照カウントをスレッド安全に増減します。
「最後の一人が使い終わったら片付ける」という約束を守ります。
ただし、`Arc` だけでは中身を書き換えられません。
共有することと、変更を安全にすることは別問題です。

告。`Mutex` は、一度に一人だけ中へ入れる門です。
解。共有した `Store` を書き換えるなら、同時更新を防がなければなりません。
`Mutex<T>` は、中の `T` にアクセスする前にロックを取ります。
ロックを持っている間、他のスレッドは待ちます。
これにより、二人が同時に同じ地図を書き換える事故を避けます。
ただしロックを長く持つと、待つ人が増えます。
安全と待ち時間のバランスが大事です。

解。`RwLock` は、読み手を複数許す門です。
読み取りだけなら、同時に何人いても状態は壊れません。
書き込みは、一人だけに制限します。
読み取りが多く、書き込みが少ない Store では候補になります。
ただし常に `RwLock` が速いとは限りません。
実装のコストや待ち方、書き込み頻度によって変わります。
まず `Mutex` で正しく作り、必要なら測って選ぶのが堅実です。

提案。ロック範囲は、できるだけ短くしてください。
共有データを読む。
必要な値を取り出す。
すぐロックを離す。
その後で文字列整形やネットワーク送信を行う。
この順番にすると、他の worker を待たせにくくなります。
ロック中に時間のかかる処理をすると、国全体の窓口が詰まります。
ロックは強い権限なので、持ち歩かないことが基本です。

告。`mpsc` は、仕事を渡すための通信路です。
解。multi-producer, single-consumer の略です。
複数の送り手から、一つの受け手へメッセージを送れます。
スレッドプールでは、接続やジョブをキューに入れ、worker が受け取って処理します。
標準ライブラリの `std::sync::mpsc` は、この考えを学ぶのに向いています。
仕事を共有変数で直接奪い合うより、チャンネルで渡す方が流れを追いやすいです。

解。worker は、仕事を待つ担当者です。
スレッドプールを作る時、最初に一定数の worker を起動します。
接続が来たら、ジョブとしてキューへ送ります。
worker はキューから受け取り、処理します。
処理が終わったら、また次の仕事を待ちます。
毎回スレッドを作るより、再利用できるため効率がよくなります。
ただし worker 数は多ければよいわけではありません。

提案。worker 数は、仮説として置いてから測ります。
CPU が多いからといって、何百個も worker を作ればよいわけではありません。
I/O 待ちが多いなら、CPU 数より多めが有利なこともあります。
CPU 計算が多いなら、多すぎる worker は切り替えコストを増やします。
教材では小さな固定数から始めます。
本番では負荷、待ち時間、メモリ使用量を見て調整します。

解。`JoinHandle` は、起動したスレッドの終了を待つための持ち手です。
スレッドを作ったら、いつ終わるかも設計に含めます。
プログラム終了時に worker を置き去りにしないことが大切です。
`Drop` を使って終了メッセージを送り、worker を `join` する設計があります。
これは少し難しいですが、運用を考えるなら避けられません。
国の仕事には、始め方だけでなく畳み方も必要です。

告。デッドロックは、互いに待ち続ける状態です。
解。スレッド A が鍵 1 を持って鍵 2 を待つ。
スレッド B が鍵 2 を持って鍵 1 を待つ。
このようになると、どちらも進めません。
これがデッドロックです。
ロックを取る順番を決める。
ロックを短くする。
複数のロックを同時に持たない。
こうした設計で危険を減らします。

解。並行処理のバグは、再現しにくいことがあります。
たまたま順番が変わった時だけ壊れるからです。
だから、設計で危険を減らすことが重要です。
共有するデータを少なくする。
状態変更を一箇所に集める。
ロック範囲を小さくする。
テストで基本契約を固定する。
この四つが、スレッドプール章の守りです。

提案。次章への橋は、運用責任です。
スレッドプールで同時接続をさばけるようになると、国は外に開けます。
外に開くと、止まった時にどう戻すかを聞かれます。
クラッシュしたらデータは残るのか。
ログは何を示すのか。
設定はどこで変えるのか。
そこで Level 8 の WAL、ログ、復旧手順へ進みます。

告。並行処理では、観測も難しくなります。
解。ログが複数スレッドから同時に出ると、順番が読みづらくなることがあります。
どの worker が処理したかを出すと、原因を追いやすくなります。
ただしログを出しすぎると、処理そのものを遅くします。
ここでも、安全、見やすさ、性能のバランスを取ります。

## 初出用語・関数の説明

- `std::sync::Arc`: 複数所有を可能にするスレッド安全な参照カウント型。
- `std::sync::Mutex`: 共有データを排他制御する型。
- `std::sync::RwLock`: 複数読み取り、単一書き込みを制御するロック。
- `std::sync::mpsc`: メッセージ送信用のチャンネルを提供するモジュール。
- `std::thread`: OS スレッドを扱う標準ライブラリのモジュール。
- `thread::spawn`: 新しいスレッドを起動する関数。
- `JoinHandle`: 起動したスレッドの終了を待つためのハンドル。
- `Box<dyn FnOnce()>`: 実行できる処理をヒープ上に置き、型を抽象化したもの。
- `Send`: 値を別スレッドへ送れることを示す trait。
- `'static`: 参照が短命な外部データに依存しないことを示すライフタイム条件。
- ロック範囲: `Mutex` や `RwLock` を保持している期間。短いほど他処理を待たせにくい。
- graceful shutdown: 処理中の仕事を壊さず、順序立てて終了する設計。

### 用語補講: 並行処理の基本語

- スレッド: プログラム内で独立して進む処理の流れです。
  複数の接続を同時に扱う時に使います。
  同時に動くため、共有データの扱いに注意します。
  速さだけでなく、安全な分担が大切です。

- スレッドプール: 先に作った複数の worker スレッドを再利用する仕組みです。
  接続ごとに新しいスレッドを作るより、作成コストを抑えられます。
  worker 数を固定できるため、資源使用量も管理しやすくなります。
  最終 KVS の同時接続処理の基礎になります。

- worker: スレッドプール内で仕事を処理する担当者です。
  キューからジョブを受け取り、実行します。
  終わったら次の仕事を待ちます。
  worker の数は性能と資源使用量のバランスで決めます。

- `Arc`: 複数スレッドで共有所有するための型です。
  最後の所有者が消えた時に中身を片付けます。
  スレッド安全な参照カウントを使います。
  ただし `Arc` だけでは中身の変更は安全になりません。

- `Mutex`: 一度に一人だけ中身へアクセスさせる同期型です。
  共有 Store を書き換える時に使えます。
  ロックを取っている間、他のスレッドは待ちます。
  ロック範囲を短くすることが性能と安全性の要点です。

- `RwLock`: 複数の読み取り、単独の書き込みを許す同期型です。
  読み取りが多い場合に候補になります。
  書き込み中は他の読み書きを止めます。
  常に `Mutex` より良いわけではないため、測定が必要です。

- ロック: 共有データへ入るための鍵です。
  鍵を持つ間だけ安全に触れます。
  鍵を長く持つと他の処理が待ちます。
  ネットワーク送信など時間のかかる処理中は、できるだけ持たないようにします。

- デッドロック: 複数の処理が互いに待ち続けて止まる状態です。
  鍵を取る順番がバラバラだと起きやすくなります。
  ロックを短くし、複数ロックを避けると危険を下げられます。
  再現しにくいので、設計で予防します。

- `mpsc`: メッセージを送るためのチャンネルです。
  複数の送り手から一つの受け手へ送れます。
  ジョブキューの学習に向いています。
  共有変数を直接奪い合うより流れが見やすくなります。

- `JoinHandle`: 起動したスレッドの終了を待つための持ち手です。
  `join` でスレッドの終了を待てます。
  プログラムをきれいに終了させる時に重要です。
  worker を作ったら、終わらせ方も考えます。

- `Drop`: 値が片付けられる時に呼ばれる仕組みです。
  スレッドプールの終了処理で使われることがあります。
  worker へ終了を伝え、`join` する設計につながります。
  「始めた仕事をどう畳むか」を表す入口です。

### 智慧之王による追加解説

`std::thread::spawn` は、新しいスレッドで処理を実行する関数です。

クロージャを渡して、その中の処理を別スレッドで動かします。

`JoinHandle` は、スレッドの終了を待つための値です。

`join` を呼ぶと、スレッドが終わるまで待ちます。

スレッドを作るにはコストがあります。

接続ごと、仕事ごとに無制限に作ると、負荷が高いときに破綻します。

そこでスレッドプールを使います。

スレッドプールは、固定数の worker スレッドを持ちます。

仕事はキューへ送られます。

worker はキューから仕事を受け取り、実行します。

標準ライブラリでは、`std::sync::mpsc` を使って仕事を送れます。

`mpsc` は multiple producer, single consumer の略です。

複数の送信者から、一つの受信者へ値を送るチャネルです。

ただし、複数 worker で受信したい場合は、受信側を `Arc<Mutex<Receiver<Job>>>` のように共有する設計がよく出ます。

この形では、仕事を受け取る瞬間だけ `Receiver` をロックします。

仕事そのものの実行中までロックし続けてはいけません。

ロック範囲が長くなり、他の worker が仕事を受け取れないからです。

### スレッドプールの形

概念としては、次のような構造です。

```rust
type Job = Box<dyn FnOnce() + Send + 'static>;

struct ThreadPool {
    workers: Vec<Worker>,
    sender: mpsc::Sender<Job>,
}
```

`Job` は、後で実行する仕事です。

`Box<dyn FnOnce() + Send + 'static>` は難しく見えます。

分解します。

`Box` は、値をヒープに置き、サイズを固定して扱うためのスマートポインタです。

`dyn FnOnce()` は、一度だけ呼べる関数のような値です。

`Send` は、別スレッドへ送れることを示すトレイトです。

`'static` は、仕事がスレッド上で必要な期間だけ有効であることを求める制約として出てきます。

序盤で完全に理解する必要はありません。

重要なのは、別スレッドへ送る仕事には、送って安全な値だけを含める必要があることです。

### 共有 Store の設計

通信サーバで共有 Store を扱うなら、次の候補があります。

```rust
type SharedStore = Arc<Mutex<Store>>;
```

または、読み取りが多いなら次も候補です。

```rust
type SharedStore = Arc<RwLock<Store>>;
```

`Mutex<Store>` の場合、GET も SET も同じ鍵を取ります。

単純で分かりやすいです。

`RwLock<Store>` の場合、GET は読み取りロック、SET や DEL は書き込みロックにできます。

読み取りが多い場合、性能が良くなる可能性があります。

ただし、ロック種別の使い分けが必要です。

設計を複雑にする価値があるか、アクセスパターンで判断します。

### ロック範囲の悪い例と良い例

悪い例。

```text
接続から読む。
Store をロックする。
命令を解析する。
Store を操作する。
応答を通信へ書く。
ログを書く。
ロックを解放する。
```

この形では、Store を使っていない時間までロックしています。

他のスレッドが待たされます。

良い方向。

```text
接続から読む。
命令を解析する。
Store をロックする。
Store を操作する。
必要な結果を取り出す。
ロックを解放する。
応答を通信へ書く。
ログを書く。
```

ロックは共有状態へ触る間だけにします。

ただし、複数操作を一つの整合した取引として扱う場合は、まとめてロックする必要があります。

短ければ常に正しいわけではありません。

整合性と待ち時間のバランスが設計判断です。

### 初出用語・関数の追加説明

- スレッド: 同じプロセス内で並行に実行される処理の流れ。
- `std::thread::spawn`: 新しいスレッドを起動する関数。
- `JoinHandle`: 起動したスレッドの終了を待つための値。
- `join`: スレッドの終了を待つメソッド。
- スレッドプール: あらかじめ用意した worker スレッドで仕事を処理する仕組み。
- worker: キューから仕事を受け取って実行する担当スレッド。
- `Arc`: スレッド間で共有できる参照カウント型。
- `Mutex`: 一度に一つのスレッドだけが値へアクセスできるようにするロック。
- `RwLock`: 複数読み取り、単一書き込みを許すロック。
- `mpsc`: 複数送信者、一つの受信者を持つチャネル。
- `Sender`: チャネルへ値を送る側。
- `Receiver`: チャネルから値を受け取る側。
- `Box`: 値をヒープに置いて扱うスマートポインタ。
- `dyn FnOnce`: 一度だけ呼び出せる関数的な値を動的に扱う型。
- `Send`: 値を別スレッドへ送れることを示すトレイト。
- ロック範囲: ロックを取ってから解放するまでのコード範囲。
- 競合: 複数の処理が同じ資源を取り合う状態。
