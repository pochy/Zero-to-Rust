## 物語パート

洞窟を出ると、森の匂いがした。

そこで出会ったのは、小さな魔物たちだった。ゴブリンたちは住処を失い、食料も道具も足りず、誰が何を持っているかすら把握できていなかった。

「つまり、在庫台帳がない」

『解。状態管理が存在しません』

「言い方が急にシステム寄りだな」

村長らしきゴブリンが、震えながら頭を下げる。

「スライム様、我らは何をどれだけ持っているのか、もう分からぬのです」

「分かった。まず台帳を作ろう」

『提案。インメモリ KVS を構築します』

「KVS？」

『解。Key-Value Store。キーと値を対応付けて保存する仕組みです』

俺は魔素を集め、森の空き地に透明な台帳を作った。

```rust
use std::collections::HashMap;

#[derive(Debug, Default)]

}
```

「名前を与えるみたいだな。キーに名前を付けて、値を置く」

『肯定。名付けは識別子を与え、管理可能にします』

ゴブリンたちは、次々に持ち物を申告した。

木材、薬草、干し肉、水袋、古い槍。

俺はそれらを `Store` に入れていった。

だが、申告はすぐに混乱した。

「木材は倉庫に三束あります」

別のゴブリンが慌てて首を振る。

「いえ、二束です。一束は柵の修理に使いました」

「薬草は十枚です」

「昨日、怪我人に使ったので七枚です」

俺はぷるんと揺れた。

数が合わない。

誰かが嘘をついているわけではない。

ただ、状態が更新されたのに、記録が更新されていないだけだ。

『告。状態と記録の不一致を確認』

「これ、思ったより重要だな」

『解。データ構造は現実の責任分担を反映します。記録が現実とずれると、判断もずれます』

村長は青い顔で膝をついた。

「申し訳ございません。長く逃げ回っていたため、誰が何を持つか決める余裕もなく」

「責めてるんじゃない。まず、状態を一箇所に集めよう」

『提案。`Store` を村の在庫の所有者にしてください』

「在庫そのものじゃなく、在庫の記録を所有するんだな」

『肯定。現物は倉庫や各家庭にあります。`Store` はその識別情報と値を保持します』

俺は、木の板にキーを書いた。

`wood`

`herb`

`meat`

それぞれに値を結びつける。

`wood` は `2 bundles`。

`meat` は `3 strips`。

ゴブリンたちは、その単純さに驚いたようだった。

「名を付けると、探しやすくなる」

『解。キーは問い合わせの入口です』

「入口がない値は、どこにあるか分からない」

『肯定。存在しても、取り出せなければ設計上は使えません』

俺は洞窟で読んだ記録を思い出した。

読める記録と読めない記録。

今度は、持っているものと持っていないもの。

世界は、思ったより「分かる形にする」作業でできている。

村の子どもが、おずおずと近づいてきた。

「スライム様。この石は、きれいだから持っていたいです」

手のひらの小石は、淡く光っていた。

「それは台帳に入れなくてもいいかもな」

『解。すべてを Store に入れる必要はありません』

「え、そうなのか？」

『肯定。管理対象を決めることも設計です。国全体で共有する必要のない個人物品まで中核 Store に入れると、責務が肥大化します』

俺は子どもに頷いた。

「それは君が持っていていい。村で共有するものだけ、台帳に入れよう」

村長が深く頷く。

「つまり、共有するものと、個人が持つものを分けるのですな」

「そう。何でも中央に集めると、逆に危ない」

『告。所有境界の理解が進行しています』

さらに、俺は操作を三つに絞った。

登録する。

読む。

消す。

増やすとか減らすとか、履歴とか、持ち主とか、やりたいことは多い。

でも最初から全部は抱えない。

まず `set`、`get`、`delete`。

小さな国には、小さな Store からでいい。

森の向こうから遠吠えが聞こえた。

牙狼族かもしれない。

村の空気が固くなる。

「在庫を把握したら、次は外の資源と危険の場所を調べる必要があるな」

『提案。探索処理へ進む前に、保存した情報を問い合わせられることを確認してください』

「台帳を作って終わりじゃない」

『解。使われるデータだけが、設計上の価値を持ちます』

ゴブリンたちは、順番にキーを読み上げた。

`wood`。

`herb`。

`meat`。

名を与え、責任を置き、共同体を始める儀式のようだった。

洞窟で得た入力は、村で状態になった。

そして足りないものを探すには、森へ出なければならなかった。

## 会話・独白パート

「でもさ、`HashMap<&str, &str>` じゃだめなのか？ 借りればコピーしなくていいし」

『警告。初心者が構造体に参照を持たせると、ライフタイム設計が急激に難しくなります』

「ライフタイム」

『解。参照がどの値に依存し、どこまで有効かを表す仕組みです』

村長が首をかしげた。

「つまり、借りた槍を台帳に登録しても、持ち主がどこかへ持っていけば台帳が壊れる、ということでしょうか」

「たぶんそう」

『肯定。台帳が責任を持って保持するなら、`String` を所有する設計が適切です』

俺は台帳に操作を追加した。

```rust
impl Store {
    pub fn set(&mut self, key: String, value: String) {
        self.data.insert(key, value);
    }

    pub fn get(&self, key: &str) -> Option<&String> {
        self.data.get(key)
    }

    pub fn delete(&mut self, key: &str) -> bool {
        self.data.remove(key).is_some()
    }
}
```

「`set` はキーと値を受け取って保存する。だから `String` を所有する」

『解。正確です』

「`get` と `delete` は探すだけだから `&str` で借りる」

『肯定。API の境界で、所有と借用を使い分けています』

ゴブリンの一人が、恐る恐る言った。

「スライム様。これで、誰が何を持っているか分かりますか？」

「ああ。少なくとも、台帳が持つべきものは台帳が持つ」

その日、村は少しだけ国に近づいた。

「大賢者、`struct` って、村で言うと何なんだ？」

『解。関連する情報をひとまとまりにした器です。村の倉庫台帳に、木材、薬草、肉の欄をまとめるようなものです』

「じゃあ `Store` は台帳そのもの」

『肯定』

「`data` は台帳の中身」

『解。`HashMap<String, String>` が、キーと値の対応を保持します』

村長が腕を組む。

「キーは品名、値は数量や説明ですな」

「そう。ただし今はどちらも文字列にしている」

『補足。最初は `String` で始め、必要になったら数量を数値型にするなど設計を進化させます』

「最初から完璧な型にしなくてもいい？」

『解。学習段階では、責務を理解できる最小構造が優先です』

ゴブタが木材を抱えながら言った。

「でも、肉を `meat` って呼ぶか `food` って呼ぶかで迷うっす」

「それ、けっこう大事だな」

『肯定。キー名は API の一部です。後から変えると利用者に影響します』

「じゃあ、命名も設計か」

『解。命名は設計です』

村長が感心したように頷く。

「名付けとは、ただ呼びやすくするだけではないのですな」

「呼び方が決まると、扱い方も決まる」

『提案。キーの命名規則を早めに決めてください』

「たとえば？」

『解。小文字英字を使う、単語区切りを `_` にする、種別を接頭辞にする、などです』

「`item:wood` とか？」

『肯定。将来、`user:1` や `config:port` のようなキーへつながります』

「今は村の在庫だけど、将来は国の設定にもなるわけか」

『解。小さな設計は、大きな設計の原型です』

俺は `get(&self, key: &str)` を指した。

「`&self` は、自分を借りるってことだよな」

『肯定。`Store` を変更せずに読むだけです』

「`&mut self` は？」

『解。自分を可変借用します。`set` や `delete` は内部状態を変えるため、変更可能な借用が必要です』

ゴブタが首をかしげる。

「可変借用って、台帳を開いて書き換える許可っすか？」

「そんな感じだな」

『肯定。読むだけの許可と、書き換える許可は分けます』

村長が真剣な顔になる。

「全員が同時に台帳を書き換えたら、混乱しますな」

「今は一人ずつでいい。後で同時に触るようになったら、別の仕組みが必要になる」

『告。その話題は並行処理の章で扱います』

「まだ先か」

『肯定。今は単一所有者の Store を理解してください』

俺は `Option<&String>` に目を留めた。

「存在しないキーは、どう表す？」

『解。`Option` です。値があるなら `Some`、ないなら `None` です』

「存在しないのに空文字を返すのは？」

『否定。空文字は値です。存在しないこととは異なります』

「なるほど。空の肉箱と、肉箱そのものがないのは違う」

ゴブタが慌てた。

「肉箱が空なのは大事件っす」

「だから区別するんだ」

『提案。`Option` を、失敗ではなく存在確認として捉えてください』

「失敗は `Result`。あるかないかは `Option`」

『解。良い整理です』

村長が台帳を見つめて言った。

「これで村の中は少し見えました。しかし、外の森には何があるか分かりませぬ」

「次は探すしかないな」

『告。探索には `Path`、`PathBuf`、再帰、部分失敗が関係します』

「また新しい言葉が増える」

『肯定。ただし、今日作った Store があるため、探索結果を保存できます』

俺は頷いた。

保存できるから、探しに行ける。

探して戻れば、また保存できる。

少しずつ、村は記憶を持ち始めていた。

## 大賢者による解説

『告。Level 3 の目的は、データを所有する境界を設計することです』

`struct` は、関連するデータをまとめる型です。`Store` は `HashMap<String, String>` を内部に持ち、保存されたキーと値を所有します。

`impl` は、その型に関連する関数、つまりメソッドを定義します。

『解。状態を持つ型を作るときは、誰がデータを所有するかを最初に決めます』

`get(&self, key: &str) -> Option<&String>` は、`Store` を変更せずに、キーに対応する値を借用で返します。キーが存在しない可能性があるため、戻り値は `Option` です。

『提案。初心者は構造体に参照を持たせる前に、所有型で設計してください。必要になってから借用範囲を狭めます』

### 補講: データに名前を与える意味

告。`struct` は、ばらばらの値に役割名を与える器です。
解。村人の名前、倉庫の在庫、登録日時、状態。
これらを個別の変数だけで持つと、関係が見えにくくなります。
`struct` にまとめると、「これは一つの概念です」とコードで表せます。
たとえば `Store` は、単なる `HashMap` ではありません。
村の情報を預かる責任を持つ場所です。
責任に名前をつけると、設計が読みやすくなります。

解。`HashMap` は、キーから値を探す地図です。
キーは名前札です。
値はその名前札に結びつく情報です。
`HashMap<String, String>` なら、文字列のキーから文字列の値を探します。
`insert` で登録し、`get` で参照し、`remove` で削除できます。
ただし、どんなキーを許すかは、`HashMap` 自身は知りません。
村の規則は、`Store` 側で決める必要があります。

提案。型は、意図を伝える看板です。
`HashMap<String, String>` と直接書くと、何の地図かわかりません。
`struct Store { data: HashMap<String, String> }` と書くと、情報を預かる倉庫だと伝わります。
さらに `impl Store` に操作を集めると、使う側は細部を知らずに済みます。
これは隠蔽です。
隠蔽は秘密主義ではありません。
安全に使える入口を用意することです。

解。`impl` は、型に機能を生やす場所です。
`impl Store` の中に `new` や `set` や `get` を書きます。
`Store::new()` は、新しい倉庫を作る関連関数です。
`store.set(key, value)` は、既にある倉庫に対するメソッドです。
メソッドの第一引数に `&self` や `&mut self` が出てきます。
`&self` は読むだけ。
`&mut self` は書き換える。
所有権の章で学んだ区別が、ここで設計になります。

告。`enum` は、取り得る状態を列挙する型です。
解。命令が `Get`、`Set`、`Delete` の三種類なら、`enum Command` にできます。
文字列のまま `"get"` や `"set"` を持ち回ると、打ち間違いに弱くなります。
`enum` にすると、Rust が「この場合を処理し忘れていないか」と助けてくれます。
`match` と組み合わせると、命令ごとの処理を明確に分けられます。
これは後のプロトコル設計でも大きな助けになります。

解。`Option` は、あるかもしれないし、ないかもしれない値です。
`HashMap::get` は、キーが存在しない場合があります。
だから、戻り値は値そのものではなく `Option<&V>` になります。
`Some(value)` なら見つかった。
`None` なら見つからなかった。
この形により、「見つからない」を普通の流れとして扱えます。
存在しないキーを読んだからといって、世界が壊れるわけではありません。
ただ、見つからなかったと判断すればよいのです。

提案。最初の KVS では、機能を増やしすぎないでください。
まず `set`。
次に `get`。
最後に `delete`。
この三つで、状態を持つプログラムの基本が見えます。
キーの正規化、保存形式、通信、復旧は後の章で扱います。
一度に全部を詰め込むと、どこで壊れたかわからなくなります。
小さく作り、小さく確かめるのが、国づくりの安全な順番です。

解。モジュール分割は、村に役所を置くようなものです。
すべてを `main.rs` に置くと、最初は楽です。
しかし処理が増えると、どこに何があるかわからなくなります。
`store`、`command`、`error` のように分けると、責任の場所が見えます。
ただし早すぎる分割も読みにくくします。
分割の合図は、「この説明を別名で呼びたい」と思った時です。

告。Level 4 への橋は、村の外側です。
解。村の KVS ができると、村の中の情報は整理できます。
しかし森全体の資源は、まだ散らばっています。
どの道に薬草があるか。
どの拠点に記録があるか。
どのファイルに必要な言葉があるか。
その探索には、`Path` と再帰処理が必要になります。
Store で「覚える」力を得たから、次は森を「探す」力へ進みます。

## 初出用語・関数の説明

- `struct`: 複数の値をまとめて名前付きの型を作る仕組み。
- `enum`: 複数の状態や種類を 1 つの型として表す仕組み。
- `impl`: 型にメソッドを定義するブロック。
- `HashMap<K, V>`: キー `K` と値 `V` を対応付けて保存する標準ライブラリのコレクション。
- `#[derive(Debug, Default)]`: デバッグ表示や初期値生成などの実装を自動生成する属性。
- `pub`: 外部モジュールから使えるように公開するキーワード。
- `&mut self`: メソッドが自身を変更するための可変借用。
- `&self`: メソッドが自身を読むだけの共有借用。
- `insert`: `HashMap` にキーと値を追加または更新するメソッド。
- `get`: `HashMap` からキーに対応する値を参照で取得するメソッド。
- `remove`: `HashMap` からキーを削除するメソッド。
- `Option<T>`: 値がある `Some(T)` と、値がない `None` を表す型。

### 用語補講: Store を支える型の言葉

- `struct`: 関連するデータをまとめて新しい型を作る仕組みです。
  `Store` のように、概念へ名前をつけられます。
  ただの値の集まりではなく、責任を持つ単位にできます。
  フィールド名は、そのデータの意味を伝える看板です。

- フィールド: `struct` の中にある個々のデータです。
  `data: HashMap<String, String>` の `data` がフィールド名です。
  名前が曖昧だと、後で読む人が迷います。
  `items`、`entries`、`data` など、役割に合う名前を選びます。

- `impl`: 型に関数やメソッドを定義する場所です。
  `impl Store` の中に `new`、`set`、`get` などを書けます。
  型と操作を近くに置けるので、設計が読みやすくなります。
  Store の規則は Store の `impl` に集めます。

- メソッド: 型の値に対して呼び出す関数です。
  `store.get("name")` のように書きます。
  第一引数に `self`、`&self`、`&mut self` などを取ります。
  読むだけなら `&self`、書き換えるなら `&mut self` が基本です。

- 関連関数: 型に関連するが、特定の値を受け取らない関数です。
  `Store::new()` のように呼びます。
  新しい値を作る時によく使われます。
  `String::from` も関連関数の例です。

- `HashMap`: キーから値を探すコレクションです。
  KVS の中心になる型です。
  `insert`、`get`、`remove` で基本操作ができます。
  キーの設計が悪いと、後で検索や上書きの意味が崩れます。

- キー: 値を取り出すための名前札です。
  KVS では `name` や `item:iron` のような文字列がキーになります。
  一意であることが期待されます。
  何をキーにするかは、データ設計の重要な判断です。

- 値: キーに対応して保存されるデータです。
  最初は `String` で十分です。
  後で構造を持たせたい場合は、独自の `struct` にできます。
  値の形式を変えると、保存や通信の設計にも影響します。

- `insert`: `HashMap` にキーと値を登録するメソッドです。
  同じキーが既にある場合、値は上書きされます。
  上書きを許すかどうかは Store の仕様として決めます。
  仕様が決まったらテストで守ります。

- `get`: `HashMap` からキーに対応する値を借りて読むメソッドです。
  戻り値は `Option<&V>` です。
  キーがない可能性があるため、値そのものを直接返しません。
  `None` を自然な結果として扱う練習になります。

- `remove`: `HashMap` からキーと値を削除するメソッドです。
  削除した値があれば返せます。
  なければ `None` になります。
  削除後に `get` すると見つからない、という仕様をテストできます。

- `enum`: 取り得る形を列挙する型です。
  `Command::Get`、`Command::Set`、`Command::Delete` のように命令を表せます。
  文字列より打ち間違いに強くなります。
  `match` と組み合わせると、命令ごとの処理が明確になります。

- `Option<T>`: 値があるかもしれないし、ないかもしれないことを表す型です。
  `Some(value)` は値ありです。
  `None` は値なしです。
  「存在しない」をエラーではなく普通の状態として扱えます。

### 大賢者による追加解説

`struct` は、複数の値を一つの意味ある単位へまとめる型です。

`Citizen` なら、名前、役割、状態をまとめられます。

`enum` は、取りうる形を限定する型です。

状態や命令のように、いくつかの選択肢から一つを選ぶ値に向いています。

`HashMap<K, V>` は、キー `K` から値 `V` を探すコレクションです。

KVS は key-value store の略で、キーと値の組でデータを保存する考え方です。

Rust の `HashMap` は `std::collections` にあります。

使うには、次のようにします。

```rust
use std::collections::HashMap;
```

`insert` は、キーと値を保存します。

同じキーがすでにある場合、古い値が置き換わります。

`get` は、キーから値を借用で取り出します。

存在しない場合があるため、戻り値は `Option<&V>` になります。

`remove` は、キーに対応する値を削除し、所有する値として返します。

存在しない場合があるため、戻り値は `Option<V>` です。

ここで `Option` が登場します。

`Option` は、値があるかないかを表します。

`Some(value)` は値あり。

`None` は値なし。

存在しないことが正常な場合、`Option` は自然な表現です。

一方、失敗理由が必要な場合は `Result` を使います。

### Store 設計の小さな設計会議

最初の設計案は単純です。

```rust
struct Store {
    citizens: HashMap<String, Citizen>,
}
```

次に、操作を `impl` にまとめます。

```rust
impl Store {
    fn new() -> Self {
        Self {
            citizens: HashMap::new(),
        }
    }
}
```

`impl` は、型に関連する関数やメソッドを書く場所です。

`new` は、新しい値を作る関連関数としてよく使われる名前です。

`Self` は、いま `impl` している型を指します。

`HashMap::new()` は、空の `HashMap` を作ります。

登録処理は、次のように考えられます。

```rust
fn add(&mut self, citizen: Citizen) {
    self.citizens.insert(citizen.name.clone(), citizen);
}
```

ここには重要な判断があります。

キーとして名前を使うため、`citizen.name.clone()` しています。

なぜ複製が必要なのか。

`citizen` 自体も値として保存するため、名前だけを同時にキーへ移せないからです。

この `clone` は、設計上のコストです。

名前をキーとして別に持つ方針なら、説明できます。

説明できない `clone` は避けるべきです。

### 命令を enum にする

Store へ届く命令も、文字列だけで扱うと危険です。

```text
add Alice scout
get Alice
remove Alice
```

この文字列を解析した後は、型へ変換したほうが安全です。

```rust
enum Command {
    Add { name: String, role: String },
    Get { name: String },
    Remove { name: String },
}
```

`Add` は名前と役割を持ちます。

`Get` は名前だけを持ちます。

`Remove` も名前だけを持ちます。

こうしておけば、`Get` に役割が必要なのか迷うことはありません。

命令の形が型で決まるからです。

### 初出用語・関数の追加説明

- `struct`: 複数のフィールドを持つ独自型を定義する仕組み。
- フィールド: 構造体が持つ名前付きの値。

- `impl`: 型に関連する関数やメソッドを実装するブロック。
- `Self`: `impl` 対象の型を表す名前。
- `pub`: 外部から使えるよう公開するキーワード。
- `mod`: モジュールを宣言するキーワード。
- カプセル化: 内部の持ち方を隠し、操作だけを公開する設計。
