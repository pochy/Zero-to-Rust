## 智慧之王による解説

『告。最終課題の目的は、これまでの Level を 1 つの設計へ統合することです』

推奨レイヤー:

```text
server 層      TCP/HTTP 接続
protocol 層    コマンドとレスポンス
store 層       データ管理と TTL
persist 層     WAL
config 層      設定
error 層       エラー型
```

データの流れ:

```text
TCP で 1 行受信
protocol が Command に変換
store が Command を実行
persist が必要な操作を WAL に追記
response を wire format に変換
TCP で返す
ログと metrics を更新
```

『解。重要なのは、どの層が何を知らないかです』

`store` は TCP を知りません。`protocol` は `HashMap` の内部を知りません。`persist` はクライアント接続を知りません。これにより、テストと変更が容易になります。

WAL 書き込みに失敗した場合、保存成功として `OK` を返すべきではありません。復旧性を保証するなら、永続化に失敗した操作は成功扱いにしない方針を明記します。

### 補講: 最終 KVS を一つの国として組み立てる

告。最終課題は、全 Level の統合です。
解。Level 0 の所有権は、Store と接続処理の責任分担に出ます。
Level 1 の出力は、ログと観測に出ます。
Level 2 の `Result` は、I/O、ネットワーク、設定読み込みに出ます。
Level 3 の `struct` と `HashMap` は、状態の中心になります。
Level 4 の探索は、ファイルや復旧データの扱いに出ます。
Level 5 の TCP は、利用者との入口になります。
Level 6 のテストは、仕様を守る盾になります。
Level 7 のスレッドプールは、同時接続を支えます。
Level 8 の WAL は、復旧の背骨になります。
Level 9 の設計判断は、範囲を守る知恵になります。

解。`server` 層は、接続を受ける場所です。
`TcpListener` で待ち受け、接続ごとに処理を worker へ渡します。
ここでは、Store の細かい実装を知りすぎないようにします。
接続を受けること。
入力を読むこと。
応答を書くこと。
この責任に集中します。
入口が太りすぎると、後からテストも変更も難しくなります。

告。`protocol` 層は、文字列と意味の変換を担当します。
解。TCP から届くのは、まず一行の文字列です。
それを `Command` に変換します。
Store の処理結果は、`Response` にします。
最後に `Response` を文字列へ戻します。
この層を分けると、ネットワークなしでパースのテストができます。
不正入力の扱いも、ここで集中的に確認できます。

解。`store` 層は、状態の唯一の管理者です。
キーと値を保存します。
TTL があるなら、有効期限も保存します。
期限切れのキーを読んだ時、消えたものとして扱います。
削除や上書きの規則もここに置きます。
外側の層が `HashMap` を直接触り始めると、規則が散らばります。
Store は国庫です。
入口は多くても、帳簿は一箇所に集めます。

提案。TTL は、最初は遅延削除で実装すると学びやすいです。
遅延削除とは、期限切れを見つけた時に無効として扱う方式です。
定期的に掃除する専用スレッドを作る方法もあります。
しかし最初から掃除スレッドを入れると、並行処理の難しさが増えます。
読み取り時や書き込み時に期限を確認する形なら、設計が追いやすいです。
必要になってから、掃除処理を追加できます。

告。`persist` 層は、WAL と復旧を担当します。
解。Store の変更命令を、再生できる形でファイルへ書きます。
起動時には、そのファイルを読んで Store を再構築します。
WAL に書く形式は、プロトコルと同じでもよいです。
ただし将来変える可能性があるなら、バージョンを持つ設計も考えます。
教材では、読みやすさと実装しやすさを優先します。
壊れた行をどう扱うかは、テストと runbook に残します。

解。`config` 層は、実行時の違いを吸収します。
ポート番号。
WAL のパス。
worker 数。
ログの出し方。
管理 HTTP の有効無効。
これらをコードのあちこちに直書きすると、変更が難しくなります。
設定としてまとめると、起動時の判断が見えます。
設定値の検証も、ここで行えます。

提案。`error` 層を軽くてもよいので意識してください。
すべてを `String` エラーにすると、最初は簡単です。
しかし I/O エラー、プロトコルエラー、設定エラーが混ざると判断しにくくなります。
標準ライブラリだけでも、`enum AppError` のように分類できます。
分類すると、ログに出す内容、クライアントへ返す内容、終了するか続行するかを分けられます。
エラー型は、失敗時の設計図です。

解。HTTP 管理 API は、人間と運用の入口です。
TCP KVS は機械向けの操作口です。
HTTP 管理 API では、ヘルスチェックやメトリクス、簡単な状態確認を提供できます。
たとえば `/health` は生存確認です。
`/metrics` は件数や処理数を返す入口です。
ただし管理 API に危険な操作を入れるなら、認証やアクセス制御が必要です。
最終課題では、範囲を絞って安全な確認機能を中心にします。

告。テストは、最終課題の受け入れ条件です。
解。`SET` して `GET` できる。
存在しないキーは `NOT_FOUND` になる。
TTL が切れた値は読めない。
WAL から復旧できる。
不正命令は `ERROR` になる。
複数接続でも Store が壊れない。
管理 HTTP が応答する。
これらをテストとして残すと、完成の意味が明確になります。

提案。最終課題では、手順書も成果物です。
起動方法。
終了方法。
サンプルコマンド。
WAL の場所。
復旧確認の方法。
ログの読み方。
既知の制限。
これらを書いておくと、ただ動くプログラムから、扱えるシステムに近づきます。

解。ログとメトリクスは、運用の目になります。
ログは、個々の出来事を追います。
メトリクスは、数値として傾向を見ます。
総リクエスト数、エラー数、現在のキー数、復旧件数。
最初は簡単なカウンタでも十分です。
大切なのは、問題が起きた時に「何も分からない」を避けることです。
観測できない国は、守れません。

告。完璧を目指して範囲を失わないでください。
解。最終 KVS は学習の総仕上げです。
本番データベースを置き換えるものではありません。
だからこそ、目的を明確にします。
標準ライブラリだけで、所有権、エラー、設計、通信、並行処理、復旧を体験する。
この目的に合わない機能は、拡張案として残します。
実装するものと、あえて残すものを分けるのもプロの判断です。

提案。完成判定は、物語の勝利条件として書いてください。
サーバーが起動する。
クライアントから操作できる。
テストが通る。
クラッシュ後に WAL から戻る。

## 初出用語・関数の説明

- TTL: Time To Live。キーが有効でいられる残り時間。
- `EXPIRE`: キーに有効期限を設定するコマンド。
- `GET /health`: HTTP でサーバーの生存状態を返す管理エンドポイント。
- `GET /metrics`: 処理件数やエラー数などの簡易指標を返す管理エンドポイント。
- `GET /keys`: 現在のキー一覧を返す管理エンドポイント。
- Metrics: システム状態を数値で観測するための指標。
- config 層: 起動アドレス、ワーカー数、保存先などの設定を扱う層。
- error 層: エラー型と変換方針をまとめる層。
- persist 層: WAL など永続化を担当する層。
- 統合テスト: TCP、Store、WAL など複数部品を組み合わせて確認するテスト。
- 運用ドキュメント: 起動、監視、復旧、制限を利用者や運用者へ伝える文書。

### 用語補講: 最終課題で統合する言葉

- TCP KVS: TCP で操作できる key-value store です。
  クライアントが命令を送り、サーバーが保存や取得を行います。
  通信、状態管理、エラー処理が一つに集まります。
  最終課題の中心システムです。

- TTL: time to live の略です。
  値が有効でいられる時間を表します。
  期限が切れた値は、存在しないものとして扱います。
  実装では現在時刻との比較が必要になります。

- 遅延削除: 期限切れを見つけた時に無効化する方式です。
  専用の掃除スレッドを作らずに始められます。
  実装が単純で、学習に向いています。
  ただし期限切れデータがしばらく残る可能性があります。

- 管理 HTTP: 運用確認用の HTTP 入口です。
  `/health` や `/metrics` のようなエンドポイントを考えます。
  KVS 操作の TCP プロトコルとは役割を分けます。
  人間や監視ツールが状態を見るために使います。

- `/health`: サーバーが生きているか確認するためのエンドポイント例です。
  複雑な情報を返す必要はありません。
  まずは `OK` のような単純な応答で十分です。
  運用ではロードバランサや監視から呼ばれることがあります。

- `/metrics`: 数値情報を確認するためのエンドポイント例です。
  リクエスト数、エラー数、キー数などを出せます。
  最初は簡単なテキストで十分です。
  観測できる情報があると、問題調査が楽になります。

- `Command`: クライアントからの命令を表す enum の設計例です。
  `Set`、`Get`、`Delete` などを型で分けます。
  文字列のまま処理するより、実装漏れを見つけやすくなります。
  プロトコル層の中心になります。

- `Response`: サーバーからの返答を表す enum の設計例です。
  成功、値あり、見つからない、エラーを表します。
  最後に文字列へ変換してクライアントへ送ります。
  内部の意味と外部表現を分けるために役立ちます。

- `AppError`: アプリケーション全体の失敗を分類する enum の設計例です。
  I/O、設定、プロトコル、復旧などを分けられます。
  どの失敗をログに出し、どれをクライアントへ返すか判断しやすくなります。
  標準ライブラリだけでも、失敗分類はできます。

- メトリクス: システム状態を数値で表したものです。
  リクエスト数やエラー数などがあります。
  ログが出来事の記録なら、メトリクスは傾向を見るための数字です。
  最初は単純なカウンタで十分です。

- 受け入れ条件: 完成と判断するための具体的な条件です。
  テストが通る、復旧できる、手順で再現できるなどです。
  曖昧な「だいたいできた」を避けられます。
  最終課題では、物語の勝利条件として扱います。

- 既知の制限: 今回あえて実装しないことを明記したものです。
  認証、暗号化、分散、圧縮などが候補です。
  書いておくと、未完成ではなく範囲判断だと伝わります。
  将来の拡張案にもなります。

### 智慧之王による追加解説

最終課題では、次の責務を分けます。

`store` は、メモリ上の key-value 状態を管理します。

`protocol` は、TCP で流れる文字列と内部の `Command`/`Response` を変換します。

`server` は、TCP 接続の受付、読み込み、応答書き込みを担当します。

`pool` は、複数接続や仕事を worker へ分配します。

`wal` は、状態変更の追記と復旧を担当します。

`admin` は、管理用 HTTP の最小応答を担当します。

`config` は、ポート、WAL パス、worker 数などを読みます。

`log` は、診断情報を人間へ伝えます。

重要なのは、依存方向です。

`store` は `server` を知らない。

`store` は `admin` を知らない。

`protocol` は TCP を知らなくてもテストできる。

`wal` は Store に適用する操作を読み書きできる。

`server` はこれらを組み合わせる。

内側の層は外側の事情を知らない方が、テストしやすく変更しやすいです。

### Command 設計

最初の命令は次の形にします。

```rust
enum Command {
    Set { key: String, value: String },
    SetEx { key: String, ttl_secs: u64, value: String },
    Get { key: String },
    Del { key: String },
    Quit,
}
```

`Set` は期限なしで保存します。

`SetEx` は TTL 付きで保存します。

`Get` は値を取得します。

`Del` は値を削除します。

`Quit` は接続を閉じます。

値に空白を許すかどうかは、仕様として決めます。

学習用の最小版では、値に空白を許さない方が実装しやすいです。

発展版では、長さプレフィックスやエスケープを導入できます。

### Response 設計

応答は次の形にできます。

```rust
enum Response {
    Ok,
    Value(String),
    NotFound,
    Error(String),
    Bye,
}
```

`Response::Ok` は操作成功です。

`Response::Value` は `GET` の成功値です。

`Response::NotFound` はキーが存在しない、または期限切れ扱いの場合です。

`Response::Error` は構文エラーや内部エラーです。

`Response::Bye` は接続終了の合図です。

wire format は、例えば次のようにします。

```text
OK
VALUE value
NOT_FOUND
ERR message
BYE
```

プロトコルは、テストで固定します。

`Response::Ok` が `"OK\n"` になること。

`Response::NotFound` が `"NOT_FOUND\n"` になること。

こうした細部が、クライアントとの契約になります。

### Store と TTL

Store の内部値は、期限を持てるようにします。

```rust
struct Entry {
    value: String,
    expires_at: Option<SystemTime>,
}
```

`SystemTime` は、システム時刻を表す標準ライブラリの型です。

`Option<SystemTime>` は、期限がある場合とない場合を表します。

`None` なら期限なし。

`Some(time)` ならその時刻を過ぎると期限切れです。

`GET` 時には期限を確認します。

期限切れなら `NotFound` として扱うか、削除してから `NotFound` を返します。

削除する場合、Store を変更するため可変アクセスが必要です。

読み取り専用 API にするなら、期限切れでも内部に残す判断もあります。

どちらにもトレードオフがあります。

学習用では、`get` の中で期限切れを見つけたら削除する設計が分かりやすいです。

ただし、`get` が状態を変更することを説明してください。

### WAL と TTL の関係

WAL には、期限付き保存の情報も残します。

相対 TTL をそのまま書くと、復旧時に期限が延びる可能性があります。

例えば、10 秒 TTL の値を保存し、8 秒後に落ちたとします。

再起動時に再び 10 秒として復旧すると、合計 18 秒残ります。

それでよいかは仕様次第です。

正確に扱いたいなら、絶対期限を書きます。

```text
SETEX_AT key unix_millis value
```

学習用では、設計を単純にするため相対 TTL から始めても構いません。

ただし、制限事項に書きます。

最終課題では、できれば絶対期限を選んでください。

その方が復旧後の意味が安定します。

### WAL 書き込み順序

状態変更は次の順にします。

```text
1. Command を受け取る。
2. 状態変更命令か判定する。
3. WAL 行へ変換する。
4. WAL へ追記する。
5. 必要に応じて flush する。
6. Store へ適用する。
7. Response を返す。
```

WAL 追記に失敗した場合、Store は更新しません。

Store を更新したあとに WAL 失敗が起きると、復旧時にその変更が消えます。

これは利用者へ成功を返していた場合、とても危険です。

そのため、WAL を先にします。

ただし、WAL に書いたあと Store 更新前に落ちた場合、復旧時にその操作が適用されます。

これを許すかどうかも設計判断です。

多くの場合、クライアントが応答を受け取る前に落ちた操作は、再実行されてもよいように設計する必要があります。

この話は難しいですが、最終課題では「どの順に何を約束するか」を必ず書いてください。

### Admin HTTP

管理 HTTP は、利用者向けの KVS プロトコルとは別の入口です。

最小版では、次だけで十分です。

```text
GET /health
GET /stats
```

`/health` は、プロセスが応答できることを返します。

`/stats` は、キー数、期限付きキー数、起動時刻、WAL パスなどを返します。

HTTP を完全実装する必要はありません。

標準ライブラリの `TcpListener` で接続を受け、リクエスト行だけを読む最小実装に限定します。

未知のパスには `404 Not Found` を返します。

メソッドが `GET` 以外なら `405 Method Not Allowed` を返す設計もできます。

ただし、admin は管理用です。

本番では認証、権限、TLS、ネットワーク制限が必要になります。

std-only 学習版では、制限事項として明記してください。

### 統合テストの地図

最終課題のテストは、層ごとに分けます。

protocol テスト。

Store テスト。

TTL テスト。

WAL 書き込みテスト。

WAL 復旧テスト。

TCP 統合テスト。

admin HTTP テスト。

ログや設定のテスト。

全部を一つの巨大なテストにすると、失敗原因が見えません。

小さなテストで部品を固め、少数の統合テストで流れを確認します。

TCP 統合テストでは、固定ポートの衝突に注意します。

`127.0.0.1:0` で OS に空きポートを割り当ててもらう方法があります。

割り当てられた実際のアドレスは `local_addr()` で取得できます。

「いい感じに復旧する」ではなく、「WAL を先頭から読み、壊れた行で起動を中止する」のように書きます。

「エラーを出す」ではなく、「`ERR unknown command\n` を返す」のように書きます。

仕様は、文字列まで決めて初めてテストできます。

### 初出用語・関数の追加説明

- TTL: Time To Live。値が有効でいられる時間。
- `SystemTime`: システム時刻を表す標準ライブラリの型。
- `Duration`: 時間の長さを表す標準ライブラリの型。
- `UNIX_EPOCH`: Unix 時刻の起点を表す定数。
- `local_addr`: ソケットが実際に使っているアドレスを取得するメソッド。
- `127.0.0.1:0`: OS に空きポートを選ばせる指定。
- health check: サービスが応答可能か確認する管理用チェック。
- stats: 稼働状態や件数などの統計情報。
- HTTP: リクエストとレスポンスで通信するアプリケーションプロトコル。
- status code: HTTP 応答の結果を表す数値。例: 200、404、405。
- 受け入れ基準: 完成とみなすために満たす条件。
- 障害演習: 意図的に停止や破損を起こし、復旧手順を確認する作業。
- レイヤー: 責務ごとに分けた実装の層。
- 依存方向: どの層がどの層を知ってよいかという関係。
- 制限事項: 現在の実装が扱わない範囲を明示したもの。

### 追加の進級チェック

次の問いに答えられたら、最終課題に着手できます。

```text
store、protocol、server、wal、admin、config の責務を分けて説明できるか。
Command と Response の wire format を一行ずつ説明できるか。
TTL を相対時間で保存する場合の復旧上の問題を説明できるか。
絶対期限を WAL に書く利点を説明できるか。
WAL 書き込み失敗時に Store を更新しない理由を説明できるか。
admin HTTP を最小実装に限定する理由を説明できるか。
固定ポートの統合テストが衝突する可能性を説明できるか。
受け入れ基準を機能一覧ではなく約束として説明できるか。
```

### 最終会議の長い対話

「智慧之王、Store はただの `HashMap` でいい？」

『解。内部実装としては可能です。ただし期限、件数、削除、復旧を考慮してください』

「Entry を持つ」

『肯定』

「GET で期限切れを見つけたら削除する」

『設計として可能です。その場合、GET が内部状態を変更することを記録してください』

「WAL に期限切れ削除も書く？」

『判断が必要です』

「書かないと、再起動後にまた残る？」

『絶対期限を保存しているなら、復旧後も期限切れとして扱えます』

「じゃあ期限切れ削除は WAL に必須ではない」

『肯定。ただし、WAL サイズ削減や compaction は別課題です』

「compaction」

『解。古いログを整理し、現在状態から新しいスナップショットや短いログへ置き換える処理です』

「今回は？」

『範囲外として制限事項に書いてください』

「バックアップは？」

『範囲外または任意発展です』

「認証は？」

『admin HTTP では本番必須ですが、std-only 学習版では範囲外として明記できます』

「TLS は？」

『標準ライブラリだけでは本格対応が難しいため、範囲外です』

「圧縮は？」

『範囲外です』

「なるほど。作らないことも仕様に入れる」

『肯定』

「じゃあ、最終課題の価値はどこにある？」

『解。所有権、失敗、型設計、I/O、通信、並行処理、永続化、運用を一つの説明可能なシステムへ統合することです』

「説明可能なシステム」

『肯定。動作だけでなく、境界と失敗を説明できることが価値です』

### 運用ドキュメントの最小形

最終課題には、短い運用メモを付けます。

```text
起動:
  tempest-kvs --addr 127.0.0.1:4000 --wal data/tempest.wal

停止:
  管理しているプロセスを通常終了する。

復旧:
  同じ WAL パスを指定して再起動する。
  起動ログに replayed entries の件数が出ることを確認する。

確認:
  TCP で GET known_key を送る。
  admin /health を確認する。

注意:
  TLS、認証、WAL compaction はこの版では未対応。
```

この運用メモは、将来の自分への手紙です。

夜中に障害が起きたとき、設計思想を読む余裕はありません。

必要なのは、正確な手順です。
