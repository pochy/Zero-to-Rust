## 智慧之王による解説

『告。Level 9 の目的は、Rust の機能を状況に応じて選べる判断力を得ることです』

ここでは、すべてを実装しきることより、設計判断を説明できることが重要です。

DNS リゾルバでは、`&[u8]` を安全に読み、境界外アクセスを避けます。Lisp インタープリタでは、`enum` と `Box` で構文木を表します。SHA-256 では、ビット演算、固定長配列、エンディアンを扱います。

『解。`Rc<RefCell<T>>` と `Arc<Mutex<T>>` は、責務を曖昧にする道具ではありません』

`Rc<T>` は単一スレッドで複数所有したいときに使います。`RefCell<T>` は実行時に借用規則をチェックし、内部可変性を可能にします。`Arc<T>` は複数スレッド用、`Mutex<T>` は排他制御用です。

`Condvar` は、条件が満たされるまでスレッドを待機させます。忙しくループして CPU を使い続けるのではなく、通知を待つ設計にできます。

### 補講: 究極能力としての「選ばない力」

告。高度な実装ほど、最初に境界を決めます。
解。バイナリ処理、DNS、SHA、Lisp、圧縮、スレッドスケジューリング。
どれも面白く、どれも学ぶ価値があります。
しかし一つの最終課題に全部を入れると、目的がぼやけます。
智慧之王が見るのは、作れるかどうかだけではありません。
今の目的に対して、作るべきかどうかです。

解。`&[u8]` は、バイト列を借りて読むためのスライスです。
文字列では扱えないデータを処理する時に使います。
ネットワーク、圧縮、ハッシュ、ファイル形式では、文字ではなくバイトを見る場面があります。
ただし `&[u8]` は、人間に読みやすいとは限りません。
文字列として扱えるかは、UTF-8 として正しいかに依存します。
KVS のプロトコルを文字列にするか、バイナリにするかは、互換性と扱いやすさの判断です。

告。`unsafe` は、速くなる呪文ではありません。
解。`unsafe` は、コンパイラが確認できない約束を人間が引き受ける印です。
使うと Rust の全ての安全性が消えるわけではありません。
しかし、そのブロック内では特別な責任が発生します。
初心者が性能目的だけで使うのは危険です。
まず安全な Rust で正しく作り、測定して、本当に必要な時だけ検討します。
最終 KVS では、原則として `unsafe` を使わない設計にします。

解。専門アルゴリズムは、仕様が本体です。
SHA のようなハッシュ関数は、少し似たものを作ればよいわけではありません。
DNS も、名前を IP に変えるだけの単純な仕組みではありません。
圧縮も、復元できれば終わりではなく、形式や互換性があります。
標準ライブラリだけで学ぶ実装は有益です。
しかし本番で必要なら、検証された実装を選ぶ判断が重要です。
智慧之王は、学習実装と運用実装を混同しません。

提案。設計判断は、理由を一文で残してください。
「HTTP 管理 API は人間が確認しやすいので採用する」
「データプロトコルは教材の明快さを優先して行単位テキストにする」
「WAL は復旧学習のために自作する」
「暗号学的ハッシュは最終課題の範囲外にする」
このように理由を書くと、後から変更する時も迷いません。
設計は、現在の知識を未来へ渡す手紙です。

解。`Condvar` は、条件が満たされるまで待つための同期道具です。
忙しく何度も確認することを busy wait と呼びます。
busy wait は CPU を無駄に使います。
`Condvar` を使うと、「仕事が来たら起こして」と待てます。
ただし正しく使うには、`Mutex` と条件確認の理解が必要です。
標準ライブラリだけでスレッドプールを深める時の発展項目です。

告。究極能力は、すべてを飲み込む力ではなく、目的に合わせて分ける力です。
解。最終課題では、TCP KVS、TTL、WAL、HTTP 管理、テスト、ログ、復旧を統合します。
DNS も圧縮も Lisp も、魅力的ですが主役ではありません。

## 初出用語・関数の説明

- バイナリプロトコル: テキストではなくバイト列で定義された通信形式。
- `&[u8]`: バイト列を借用するスライス型。
- エンディアン: 複数バイトの数値をどの順序で並べるかの規則。
- `Box<T>`: 値をヒープに置き、所有するスマートポインタ。
- `Rc<T>`: 単一スレッドで複数所有を可能にする参照カウント型。
- `RefCell<T>`: 借用ルールを実行時にチェックして内部可変性を提供する型。
- `Condvar`: 条件変数。条件が満たされるまでスレッドを待機させる同期プリミティブ。
- `unsafe`: Rust の一部安全チェックを開発者責任にするブロックや関数。
- 境界チェック: 配列やバイト列を読む前に、有効範囲内か確認すること。
- 構文木: プログラムや式の構造を木として表したデータ。
- ワークスティーリング: 空いたワーカーが他のワーカーのキューから仕事を取る並行処理方式。

### 用語補講: 高度設計で出る言葉

- `&[u8]`: バイト列を借りて読むスライスです。
  文字列ではないデータを扱う時に使います。
  ネットワークやファイル形式、ハッシュ処理でよく出ます。
  UTF-8 として正しいとは限らない点に注意します。

- バイナリ処理: 文字ではなくバイト単位でデータを扱うことです。
  画像、圧縮データ、暗号、独自プロトコルなどで必要になります。
  人間には読みにくい代わりに、効率や表現力を得られます。
  教材の最終 KVS では、まず読みやすいテキストを優先します。

- DNS: ドメイン名を IP アドレスなどへ変換する仕組みです。
  単純な表引き以上に、キャッシュや問い合わせ形式など多くの仕様があります。
  学習実装はできますが、本番では検証済みの実装を使う判断が重要です。
  Level 9 では「範囲を見極める例」として扱います。

- SHA: 暗号学的ハッシュ関数の一群です。
  入力から固定長の値を作ります。
  少し似た処理を自作しても、同じ安全性にはなりません。
  セキュリティに関わる実装は、特に慎重に選びます。

- Lisp: リスト構造を中心にした歴史あるプログラミング言語の系統です。
  パーサーや評価器の学習題材としてよく使われます。
  Rust で作ると enum、Box、再帰構造を学べます。
  ただし最終 KVS の主目的とは分けます。

- 圧縮: データを短く表現する技術です。
  保存量や通信量を減らせます。
  ただし CPU 時間、形式互換性、復旧性との tradeoff があります。
  WAL に圧縮を入れるなら、壊れた時の扱いも考えます。

- `unsafe`: コンパイラが確認できない安全条件を人間が引き受ける印です。
  速くなる保証ではありません。
  使うなら、なぜ安全と言えるかを説明する必要があります。
  最終課題では原則使わず、安全な Rust で設計します。

- `Condvar`: 条件が満たされるまでスレッドを待たせる同期道具です。
  busy wait を避けるために使われます。
  `Mutex` と組み合わせて使うことが多いです。
  正しく使うには、待つ条件を明確にする必要があります。

- busy wait: 条件が満たされたかを何度も確認し続ける待ち方です。
  CPU を無駄に使いやすいです。
  簡単ですが、運用では問題になることがあります。
  条件変数やチャンネルで待つ設計を検討します。

- tradeoff: 片方を得ると別の何かを支払う関係です。
  速さと分かりやすさ、耐久性と実装量などがあります。
  正解を暗記するのではなく、状況に合わせて選びます。
  プロの設計判断では必ず出てくる考え方です。

### バイナリ処理の入口

文字列は人間に読みやすい形式です。

しかし、ネットワークやファイル形式には byte 単位のデータが多くあります。

Rust では `u8` が 1 byte の整数型です。

`Vec<u8>` は所有する byte 列です。

`&[u8]` は借用された byte 列です。

`read_exact` は、指定した長さだけ読み込むメソッドです。

短い読み込みを許さないため、バイナリ形式の固定長ヘッダを読むときに便利です。

整数は endian を考える必要があります。

endian は、複数 byte の整数をどの順で並べるかの規則です。

Rust の整数型には、`from_be_bytes` や `from_le_bytes` があります。

`be` は big-endian。

`le` は little-endian。

通信プロトコルでは big-endian が使われることが多いです。

ただし、必ず仕様を確認します。

### unsafe の考え方

`unsafe` は、Rust が普段守っているいくつかの安全条件を、プログラマが保証する領域です。

`unsafe` を使うと、コンパイラが止めていた操作の一部が可能になります。

だから速くなる可能性があります。

だから低レベルな操作ができます。

同時に、未定義動作の危険も出ます。

学習段階では、`unsafe` を使わずに設計できるなら使わない方がよいです。

使う場合は、次を書きます。

```text
なぜ safe Rust では足りないのか。
unsafe ブロックの安全条件は何か。
呼び出し側に何を要求するのか。
どのテストで守っているか。
どのレビューで確認したか。
```

`unsafe` は魔王の力ではありません。

監査対象の契約です。

### 初出用語・関数の追加説明

- std-only: 外部クレートを使わず、標準ライブラリだけで作る方針。
- byte: 8 bit のデータ単位。Rust では主に `u8` で扱う。
- `Vec<u8>`: 所有する byte 列。
- `&[u8]`: 借用された byte 列。
- `Read`: 読み込み操作を表す標準ライブラリのトレイト。
- `Write`: 書き込み操作を表す標準ライブラリのトレイト。
- `read_exact`: 指定した長さだけ読み込むメソッド。
- endian: 複数 byte の整数を並べる順序。
- `from_be_bytes`: big-endian の byte 列から整数を作る関連関数。
- `from_le_bytes`: little-endian の byte 列から整数を作る関連関数。
- DNS: ドメイン名を IP アドレスなどへ対応づける仕組み。
- SHA: ハッシュ関数の一群。暗号用途では信頼できる実装が重要。
- Lisp: S 式を中心とするプログラミング言語系統。
- 圧縮: データをより短い表現へ変換する処理。
- `unsafe`: 一部の安全条件をプログラマが保証する Rust の領域。
- 未定義動作: 言語仕様上、結果が保証されない危険な動作。
- 監査: 実装や設計を安全性、正しさ、リスクの観点で確認すること。
